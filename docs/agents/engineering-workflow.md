# Engineering skills 工作流

本文件是 LazyCat 对 `mattpocock/skills` 的仓库级适配层，负责把规格、工单、诊断、实施和评审路由到现有项目约束与经验。根目录 `AGENTS.md` 的硬约束优先；相关代码、配置和测试仍是实现事实源。

关键词：`to-spec`、`to-tickets`、`diagnosing-bugs`、`implement`、`code-review`、`AGENTS.md`、`dirty worktree`、`read-only`、`handoff`、`regression`、`commit`、`verification`

## 技能路由

所有工程技能先读取 `AGENTS.md`，再按下表读取任务上下文。`CONTEXT.md` 只提供领域术语，`docs/adr/` 只提供仍有效的架构决策，`docs/experience/` 提供与当前任务相关的实现和排障经验；三者不能互相替代。

| 技能 | 使用前提 | 必读上下文 | LazyCat 约束 |
| ---- | -------- | ---------- | ------------ |
| `to-spec` | 当前对话已经解决会影响行为、范围和验收的决策 | `CONTEXT.md`、相关 ADR、相关经验、当前代码与测试 | 只综合已确认内容；仍有关键歧义时列出缺口并停止发布。测试接缝经用户确认后，规格写入 `.scratch/<feature>/spec.md`。 |
| `to-tickets` | 规格、计划或当前对话已经形成明确实施边界 | 原始规格、`docs/agents/issue-tracker.md`、相关领域文档 | 先让用户确认纵向切片和阻塞关系，再按依赖顺序写入 `.scratch/<feature>/issues/`；工单不复制易失效的文件路径和代码片段。 |
| `diagnosing-bugs` | 用户报告故障、失败或性能回退 | 相关经验、用户真实路径、最低稳定测试层 | 先建立能命中原始症状的紧反馈回路，再复现、缩小和验证假设。只授权诊断时停在根因与证据，不进入修复；授权修复时再补回归测试并完成清理。 |
| `implement` | 用户已经授权实施，且规格或工单边界已确认 | 规格/工单、相关经验、目标文件与测试、当前工作区 diff | 在约定接缝优先使用 TDD；没有独立 `tdd` 技能时直接使用仓库现有测试命令，不因此跳过红绿验证。定向测试后运行适用的类型检查和构建，以实施前基线评审全部任务差异，通过后仅提交当前任务文件。 |
| `code-review` | 用户给出固定点，或实施流程已记录实施前基线 | `AGENTS.md`、本文件、相关经验、规格/工单、差异与提交列表 | 除 `<fixed-point>...HEAD` 的提交差异外，还要读取任务相关的 staged、unstaged 和 untracked 变更，WIP 评审不得只检查 `HEAD`。Standards 轴检查仓库硬约束和相关领域经验；Spec 轴检查遗漏、错误实现和范围扩张。每个轴内部按严重度呈现，不跨轴重排，也不把测试、类型检查或构建通过当成行为验收。 |

### 经验选择

先通过 [经验索引](../experience/README.md#领域索引) 选择与任务直接相关的文件，不扫描或加载全部历史。常见路由如下：

- 跨层架构、IPC、Tauri、迁移和结构治理：`docs/experience/architecture.md`
- UI、响应式、滚动和 Element Plus：`docs/experience/ui-and-styling.md`
- 并发、后台状态和长生命周期服务：对应领域经验，以及本文件的状态不变量章节
- Windows 构建、打包和发布：`docs/experience/windows-build-and-release.md` 与 `docs/experience/release-package.md`

## 根规范是执行入口，不是知识仓库

根规范只保留高频、稳定、会改变执行决策的规则；领域架构和排障细节放入 `docs/experience/`。索引按任务类型组织，避免 agent 每次扫描整份历史。

## Agent 规则使用单一事实源

跨 Agent 的项目规则只维护在 `AGENTS.md`。`CLAUDE.md` 仅通过 `@AGENTS.md` 提供 Claude Code 加载适配；修改规则时检查适配入口仍有效，不复制规则正文。

## dirty worktree 先划定边界

开始前记录 `git status --short` 和相关 diff。现有改动属于用户，任务文件单独暂存；遇到目标文件已有改动时先读 diff，把它纳入迁移或明确避让。

## worktree 获批后再初始化

默认在当前工作区和分支完成任务。只有当前工作区无法安全完成、并行修改存在明确冲突或流程强制隔离时，才可说明必要原因、影响范围、替代方案和清理方式并申请 worktree；未经用户明确同意不得创建。

用户同意后只运行 `pnpm install --frozen-lockfile --prefer-offline` 初始化依赖，不执行 `pnpm build`、Tauri build 或安装包构建；随后按任务范围做定向验证。本机已安装 `sccache` 时，通过用户级 `RUSTC_WRAPPER=sccache` 复用 Rust 编译缓存，各 worktree 保持独立 `target`，不把 `sccache` 设为项目依赖。

## 只读请求与实施授权分离

“调研、规划、评审、检查、解释、复盘、报告状态”默认只授权读取事实和输出结论，不授权修改代码或文档，也不授权提交、合并、推送、打包或发布。用户同一请求明确要求落地时，先完成必要的方案确认，再进入写操作；不能把“给出修复建议”自行解释为“直接修复”。

## 已确认规格是执行边界

用户已经确认规格或实施计划时，先核对最新指令、当前代码和仓库状态。没有冲突就按已确认文档执行，不重新设计、不增加阶段、不顺带扩展；发现文档与代码事实冲突、验收缺项或关键前提失效时，列明差异并暂停确认。

## Sol-Luna 按复杂度和额度分工

Sol 始终使用 `xhigh`，负责复杂思考、复杂实现、需求与架构取舍、根因诊断、并发/事务/兼容性/安全/解析器/文件系统语义、任务冻结和最终审查；项目默认值由 `.codex/config.toml` 固定。Sol 必须先完成研究、决策和直接可执行的详细设计，再冻结任务包并把有界执行交给 Luna。Luna 只负责简单、边界冻结、低风险且可确定性验收的实施或只读分析，不补设计空白；极小任务由 Sol 直接完成，避免交接本身消耗更多 token。难以判断执行者时选 Sol，不能用 Luna `xhigh` 承接复杂任务。

Luna 由个人级 `~/.codex/agents/default.toml` 固定为 `gpt-5.6-luna` 和 `xhigh`，适用于已冻结、可确定性验收的多文件、耗时简单实施或证据源和分类规则明确的只读分析。主代理通过 `spawn_agent` 启动默认子代理，使用 `fork_turns = "none"` 并直接传递完整冻结任务包，不复制主线程历史，也不通过调用参数覆盖模型或推理强度。使用 Luna 的前提是没有需求歧义、不涉及复杂根因、架构、数据模型、并发、事务、兼容性、安全、解析器、文件系统语义或高风险决策，输入输出与验收均确定，错误可被确定性检查发现且失败可安全停止。只有一两个命令的小任务由 Sol 直接完成，避免交接开销。

任务包必须完整、明确且可直接执行，至少包含任务类型、目标、上下文、已确认决策、`Executable Design`、非目标、允许与禁止范围、`Allowed Changed Paths` JSON 数组、步骤、验收标准、验证、停止条件和输出证据。`Executable Design` 由 Sol 冻结：实施任务写明精确目标文件及相关符号/区段、必要改动、适用的行为/数据/控制流契约、边界/失败/兼容性约束和测试改动或验证顺序；只读任务写明精确证据源、搜索/检查方法、适用的分类/去重规则和完整性检查。`Steps` 只表达执行顺序，不替代详细设计，也不把方案选择交给 Luna。实施任务逐项列出允许修改的仓库相对文件，不得用“对应测试”“相关文件”等占位文本；路径未知时由 Sol 先查明。只读任务固定为 `[]`。完整不等于复制全部线程或源码；优先引用本地文件，只传冻结结论和执行所需上下文。信息不足时由 Sol 补齐，不能要求 Luna 自行理解需求。

Git 工作区是唯一事实源。Luna 不提交、不回滚用户改动、不创建下级代理；只读任务不得改变工作区，写入任务同一时间只允许一个执行代理。Sol 在委派前记录 `git status --short`、`HEAD` 和任务相关 diff，保存 `spawn_agent` 返回的 agent id，并使用 `wait_agent` 等待；只发送不改变设计的补充事实，机械修正才可通过 `followup_task` 交给同一 agent。Luna 返回后，Sol 对账委派前基线、真实状态、`HEAD`、完整 diff、`Allowed Changed Paths` 和 Luna 摘要，抽查分析证据并复跑关键验证。只读任务出现改动、实施任务越界或 Luna 创建提交时立即停止验收，不自动回滚或改写历史。`blocked`、`failed`、超时或工具异常不触发自动换模型或重建代理；先检查事实，只有设计不变的机械问题允许最多一次有界补充执行。Luna 不可用、个人默认代理配置不匹配或执行中出现新决策时显式阻塞，不静默回退到其他模型。

具体路由、任务模板、`spawn_agent` 编排和结果契约见 [sol-luna-delivery](../../.codex/skills/sol-luna-delivery/SKILL.md)。

## 续作与交接以仓库事实为准

“继续”或“确定”只延续最近一次已确认范围。跨对话续作先读取权威规格/计划、相关提交、`git status`、目标 diff 和最近验证结果，不依赖上一轮自然语言总结猜测进度。

用户要求当前工作情况或下一轮对话 prompt 时，交接内容至少包括：当前目标与非目标、权威文档、基线和相关提交、dirty 状态、已完成项、剩余步骤、已运行及未运行的验证、下一步入口。不得把未提交修改写成已完成提交，也不得在交接文本中带入秘密。

## 范围升级先重新定界

专用功能升级为通用架构，或新增持久化、后台执行、并发、恢复等能力时，先暂停实现并集中输出一次范围摘要：

```text
当前目标：本阶段必须交付的用户结果
MVP：实现该结果所需的最小能力
后续阶段：有价值但不阻塞当前结果的能力
非目标：明确不做的行为
影响范围：涉及的领域、持久化、IPC 和 UI 边界
最低验证：本阶段完成的证据
```

如果用户已经明确选择，不重复询问。用户回复“继续”或“确定”后，按已确认摘要执行到下一个会改变用户行为、数据模型、架构边界、破坏性操作或外部副作用的决策点；低风险实现细节由 Agent 基于现有代码处理。

## 状态型功能先明确不变量

涉及并发、后台执行、事件、轮询或事务时，编码前回答：

- 哪个存储或对象是唯一事实源，缓存和事件只承担什么角色；
- 谁创建、持有和释放运行状态，成功、失败、panic 和启动失败路径是否都能释放；
- 哪些读取与写入必须处于同一事务，是否存在校验后状态变化的 TOCTOU；
- 并行 worker 是否共享不可跨线程资源，单个失败是否与其他步骤隔离；
- 事件、轮询和请求晚响应如何避免旧状态覆盖新状态；
- 页面卸载、监听重建和应用重启后的状态如何收口。

同一边界连续出现两个并发、事务或状态一致性问题，说明不变量或时序仍不完整。此时停止叠加局部补丁，重新检查所有权、事务边界和交错路径。

## 复杂状态功能按风险前置审查

1. 数据模型、事务边界和状态机骨架完成后，先审查不变量及交错时序。
2. 领域执行与 UI 接通后，审查跨模块契约和用户反馈。
3. 最终交付或合并前，审查最终差异、遗漏测试和工作树边界。

修复审查问题后先验证受影响边界；除非修改触及共享契约或构建链，不重复执行未受影响的完整验证。

## 错误显式暴露

错误返回保留动作、目标和失败阶段等必要上下文，不能用默认值、空结果、静默 catch 或成功状态掩盖失败。仅明确属于非关键、可降级的 best-effort 路径允许继续执行，但必须记录可诊断信息，并保证降级结果不会被解释为完整成功。

## 用户反馈未解决时旧结论失效

用户明确反馈问题仍存在后，之前的“根因已确认”“修复已验证”和静态检查不能继续作为完成证据。停止沿原假设叠补丁，回到用户真实路径重新复现，核对运行状态、持久化数据、权限、缓存和事件时序，再形成新的可证伪假设。

## 验证基于证据

验证分为三级：

| 级别     | 触发时机                           | 验证范围                                                     |
| -------- | ---------------------------------- | ------------------------------------------------------------ |
| 定向验证 | 每个局部实现或修复后               | 对应单元测试、契约测试或最小检查                             |
| 阶段验证 | 一个数据层、执行层或 UI 阶段完成后 | 相关测试集合；涉及代码和类型表面的阶段运行对应范围的类型检查 |
| 最终验证 | 功能验收完成、提交或合并前         | 任务要求的完整测试、类型检查、构建和 `git diff --check`      |

Bug 修复先在用户路径或最低稳定层复现根因，再在该层补回归测试。无法可靠自动化时记录限制和原因，并执行步骤明确、可重复的最小冒烟；不能用更宽泛但未覆盖故障路径的测试代替。

失败必须显式报告。分层验证只减少无影响范围的重复执行，不允许省略任务要求的最终验证，也不把静态阅读或未运行命令描述为“已验证”。文档迁移继续使用数量对账、链接检查、规则关键词检查和差异边界检查。

## 阶段完成主动提交

实施任务形成可独立验收、可回退的阶段结果并通过相关验证后，主动创建提交，不等待用户再次发出提交指令。进入高风险或大范围后续工作前，如果当前结果已形成可靠基线，也应先提交再继续。

提交前检查 `git status`、当前任务 diff、验证结果和 `git diff --check`，只暂存当前任务文件；无关改动、秘密、临时文件和无关生成物继续留在工作区。失败、未验证、不可运行或边界尚未确认的中间态不提交。

主动提交只创建新的本地 commit，不自动推送、合并、打包或发布。未经用户明确要求，不执行 amend、rebase、squash、force push 或其他历史改写；提交失败时显式报告，不跳过钩子或降低校验绕过问题。
