## 一、功能目标

用户输入 URL、域名或 IP 后，按照真实访问链路逐层诊断：

代理
→ Hosts
→ DNS
→ TCP
→ TLS
→ HTTP

最终给出：

1. 每一层的检测结果和原始证据。
2. 请求失败的准确阶段。
3. 可理解、可验证的结论。
4. 推荐的下一步排查操作。
5. 可复制或导出的离线诊断报告。

示例：

目标：https://api.dev.local:8443/health

1. 代理
   命中 NO_PROXY *.local，本次直连

2. Hosts
   命中 api.dev.local → 10.20.30.40

3. DNS
   内网 DNS 返回 10.20.30.41，与 Hosts 不一致

4. TCP
   10.20.30.40:8443 连接成功，耗时 8ms

5. TLS
   握手成功，但证书 SAN 不包含 api.dev.local

6. HTTP
   返回 502，上游连接失败

结论：
当前请求受 Hosts 覆盖，并且目标服务证书与访问域名不匹配。

### 1.1 原位替换与兼容要求

- 保留工具 ID `network`，将菜单名称和描述更新为“访问链路诊断”，避免破坏工具收藏、点击历史、菜单显隐、标签页和 Spotlight/快捷入口中对工具 ID 的引用。
- 不新增一个并列的“访问链路诊断”菜单，也不让旧 `NetworkPanel` 与新面板长期双轨运行。
- 明确现有 PING、TCP、UDP、快捷端口、收藏、最近 50 条历史、筛选、失败批量复测等能力的“保留 / 合并 / 降级 / 移除”矩阵。替代功能不能在未说明的情况下丢失已有能力。
- 推荐将 PING、TCP、UDP 保留为页面内的“单项探测 / 快速探测”，完整 URL 走“链路诊断”；UDP 必须使用“收到响应 / 明确拒绝 / 无响应无法判断”等三态语义，不能再把无响应等同于可达。
- 规划旧设置数据的一次性、幂等迁移。不得静默删除或覆盖 `network_test_favorites`、`network_test_history`；新收藏需能表示 URL、连接 IP、SNI、Host、代理策略等字段，并带 `schemaVersion`。
- `network.rs` 还承载 `http_status_list`、`http_status_lookup`、`chmod_calc`，分别被其他面板使用。规划模块拆分或收口时必须保留这些 action 的兼容性，不能整模块删除。
- 明确旧 `tcp_test`、`udp_test`、`ping_test`、`http_test` action 的过渡期、内部复用方式和最终删除条件；不要永久保留两套事实源。

### 1.2 访问链路不是固定直线

页面可以用“代理 → Hosts → DNS → TCP → TLS → HTTP”帮助理解，但执行模型必须是带条件分支的有向步骤图，不能伪造一条所有场景都经过的线性链路：

- 直连 HTTPS：本机有效解析（Hosts/系统解析）→ 目标 TCP → TLS → HTTP。
- HTTP 代理访问 HTTP：本机只连接代理，目标域名可能由代理解析；目标 TCP/DNS 不一定能被本机直接观测。
- HTTP 代理访问 HTTPS：代理解析与连通 → 代理 TCP → CONNECT → 目标 TLS → HTTP。
- SOCKS4/SOCKS5、远端 DNS 与本地 DNS 的语义不同；MVP 若不支持，必须显式标为不支持，而不是按 HTTP 代理推断。
- “旁路 DNS 查询”“忽略 Hosts 直连指定 IP”“直连/代理对比”属于对照实验，必须与操作系统实际访问路径分栏展示，不能混入主链路后得出错误因果结论。
- 后续步骤因前置失败而未执行时标为 `blocked` 或 `skipped`，并记录阻断来源；不能显示成失败或无数据。

## 二、输入方式

规划以下输入：

- 完整 URL
- 域名
- IPv4
- IPv6
- IP + 端口
- 域名 + 端口

需要明确不同输入下：

- 默认协议和端口如何确定
- 是否执行 TLS/HTTP
- 用户如何指定连接 IP、SNI 域名和 HTTP Host
- 参数缺失时如何显式提示，而不是隐式猜测

输入归一化还需要覆盖：

- IPv6 `host:port` 必须使用 `[IPv6]:port`，并说明链路本地地址的 scope ID（如 `%12`）是否进入 MVP。
- URL 中的 IDN/Punycode、尾点域名、大小写、默认端口、路径、查询参数、fragment、userinfo 的归一化与报告脱敏规则。
- 裸域名或裸 IP 没有协议/端口时，优先让用户选择“仅解析 / PING / TCP / 完整 HTTP(S) 诊断”；如果提供智能默认值，必须在执行前展示推导结果并允许修改。
- “连接 IP”只覆盖建立 TCP 的目的地址，不应悄悄改写证书校验名、SNI 或 HTTP Host。

重点支持以下高级场景：

连接地址：10.20.30.40:443
SNI：api.dev.local
HTTP Host：api.dev.local

借此区分：

- IP 是否可达
- SNI 是否选择了正确虚拟主机
- 证书是否匹配业务域名
- HTTP Host 路由是否正确

## 三、代理诊断

需要调研并规划：

- Windows 用户代理（WinINET）
- WinHTTP 代理
- 环境变量：
  - HTTP_PROXY
  - HTTPS_PROXY
  - ALL_PROXY
  - NO_PROXY
- PAC 自动配置脚本
- WPAD 自动检测
- 代理绕过规则
- Git、npm/pnpm、Maven、Gradle 代理作为后续扩展

核心不是只展示配置，而是计算：

> 对当前目标 URL，系统或指定客户端实际应该走代理还是直连。

需要考虑：

- 系统代理与 WinHTTP 配置不一致
- 大小写环境变量
- NO_PROXY 的域名、后缀、IP、端口和 CIDR 规则
- PAC 获取或执行失败
- 代理 DNS 是否可解析
- 代理端口是否可连接
- HTTP CONNECT 是否成功
- 407 代理认证
- 直连与代理对比测试
- 不同客户端不一定采用相同代理配置

必须先定义“客户端配置画像”，至少区分：Windows 用户代理、WinHTTP、环境变量兼容客户端、LazyCat 手动指定。不存在对所有应用都成立的唯一“实际代理”。结论必须包含所选画像、命中的配置来源、规则优先级和无法确定项。

PAC/WPAD 规划必须说明：

- 使用 Windows API 解析还是自行获取/执行；禁止用不受控的通用 JS `eval` 执行 PAC。
- PAC 获取、执行和返回多个代理候选时的超时、失败与降级语义。
- WPAD、PAC、AIA/CRL 等可能产生额外网络请求，UI 和报告中应能识别这些辅助请求。
- 代理 URL 或环境变量中可能含凭据，界面、日志、历史和导出报告必须脱敏。

禁止在诊断过程中自动修改系统代理。

## 四、Hosts 诊断

复用现有 Hosts 工具和数据结构，规划：

- 目标域名是否命中系统 Hosts
- 最终命中的 IP
- 同一域名重复配置
- 同一域名映射到多个 IP
- IPv4/IPv6 冲突
- 格式错误或不可见字符
- 被注释但与当前目标相关的记录
- Hosts 与 DNS 结果不一致
- Hosts 目标 IP 的端口是否可达
- 当前启用的 Hosts 配置来源

诊断器不能为了测试直接修改 Hosts。

如需比较“忽略 Hosts 后的结果”，应由诊断器直接使用 DNS 返回的 IP 建立测试连接，不修改系统文件。

## 五、DNS 诊断

规划以下能力：

### 系统信息

- 每张网卡配置的 DNS 服务器
- 网卡优先级
- DNS 搜索后缀
- IPv4/IPv6 状态
- Windows DNS 缓存
- VPN 注入的 DNS
- DoH 配置
- NRPT 规则

需要区分 MVP 必做项和后续增强项。

必须把两类结果分开建模：

- **有效解析**：操作系统对当前访问实际采用的结果，可能受 Hosts、搜索后缀、缓存、NRPT、VPN 和 DoH 影响。
- **旁路 DNS 查询**：直接向指定 DNS 服务器发起的 A/AAAA/CNAME/PTR 查询，用于对照，不代表应用最终一定采用。

现有 `dns.rs` 可作为复用起点，但当前多种 RR 查询把错误转换为空数组。规划必须改成可区分 `no_records`、`nxdomain`、`servfail`、`refused`、`timeout`、`malformed_response`、`transport_error` 的显式结果，不能直接复用现有空数组语义。

### DNS 查询

首期支持：

- A
- AAAA
- CNAME
- PTR

后续考虑：

- SRV
- TXT
- MX
- NS
- SOA

查询结果显示：

- 查询服务器
- 响应时间
- TTL
- CNAME 链
- 最终 IP
- NXDOMAIN
- SERVFAIL
- REFUSED
- 超时
- 格式错误

禁止将查询失败静默显示为“无记录”。

### 多 DNS 对比

支持分别查询：

- 系统默认 DNS
- 指定内网 DNS
- VPN DNS
- 用户手动输入的 DNS

明确展示不同服务器返回结果是否一致。

## 六、IP 对应域名发现

不要承诺“查询该 IP 的全部域名”。

规划“候选域名发现”：

- PTR 反向 DNS
- 系统 Hosts
- Windows DNS 缓存
- LazyCat 本地历史解析记录
- 后续支持导入 BIND/Windows DNS 区域文件
- 后续从证书 SAN、项目配置或日志提取候选域名

每个候选域名必须展示来源，例如：

- PTR
- Hosts
- DNS 缓存
- 历史记录
- 证书 SAN
- 导入的 DNS 区域

对候选域名执行正向验证：

候选域名
→ 查询 A/AAAA
→ 判断结果是否仍包含目标 IP

状态至少区分：

- 双向一致
- Hosts 命中
- 当前解析已变化
- 仅证书声明
- 无法验证

需要说明 PTR 查询容易实现，但不能代表指向该 IP 的所有域名。

## 七、TCP 诊断

规划：

- IPv4/IPv6 连接
- 指定端口
- 连接超时
- DNS 结果包含多个 IP 时逐个测试
- 连接耗时
- 拒绝连接、超时、路由不可达等错误分类
- 代理连接与目标连接分开显示
- 支持取消正在执行的检测
- 限制并发和超时时间

首期不做：

- 全网端口扫描
- 大范围网段探测
- 未经确认的批量连接

作为旧功能的原位替代，还需明确：

- PING 是否进入首期单项探测；若保留，应复用 Windows ICMP API，但补齐域名解析、每包结果、超时与取消语义。
- UDP 是否进入首期单项探测；若保留，必须明确其结果通常只能是“有响应”“明确不可达”“无响应无法判断”，不能承诺检测端口开放。
- 多地址探测应设置小并发上限并保留地址族、目标 IP、错误码和耗时，不能只聚合成一个 `reachable` 布尔值。

## 八、TLS 和证书诊断

规划远程 TLS 服务检查：

- TLS 握手是否成功
- TLS 版本
- 完整证书链
- Subject、Issuer
- SAN
- 有效期
- 距离过期天数
- 主机名匹配
- Windows 证书信任状态
- 中间证书缺失
- EKU
- 签名算法和密钥长度
- SNI 开启与关闭的差异
- 系统时间异常对证书验证的影响

必须分别规划“直连目标 TLS”和“经代理 CONNECT 后的目标 TLS”，并保留实际对端 IP、SNI、校验主机名和证书链来源。连接 IP、SNI、证书主机名校验必须是三个独立字段。

吊销状态必须区分：

- 已确认有效
- 已确认吊销
- 无法离线验证
- 检查端点不可达

不能把“无法验证吊销状态”直接显示成“证书无效”。

需要调研 Rust/Tauri 下如何复用 Windows 证书存储完成信任验证，避免自行实现不完整的证书链判断。

## 九、HTTP 诊断

规划：

- GET/HEAD 的选择
- 状态码
- 总耗时
- 关键响应头
- 重定向链
- 是否通过代理
- 实际连接 IP
- SNI 和 Host
- HTTP 与 HTTPS
- 代理认证失败
- TLS 失败时不伪造 HTTP 结果
- 响应体读取上限
- 防止下载大文件
- 用户取消

HTTP 安全与边界要求：

- MVP 默认不发送 Cookie、Authorization、自定义凭据和请求体；若后续支持，必须默认从历史、日志和报告中排除。
- 限制重定向次数、单次/整体超时、响应头大小和响应体读取字节数；报告每一跳的 URL、状态、连接 IP 和代理，但对查询参数中的敏感值做脱敏。
- 明确 HEAD 失败或返回 405 时是否用受限 GET 重试，不要把“HEAD 不支持”误判为站点不可访问。
- 跨协议降级、跨主机重定向和访问本机/内网地址是诊断工具的正常场景，但必须可见且不自动携带敏感头。

结果需要明确区分：

- 代理失败
- DNS 失败
- TCP 失败
- TLS 失败
- HTTP 协议失败
- 应用返回 4xx/5xx

## 十、诊断执行模型

规划任务执行方式：

- 各检测步骤的依赖关系
- 哪些步骤可以并行
- 哪些步骤必须串行
- 单步超时
- 整体超时
- 取消机制
- 进度展示
- 重试策略
- 单步重新检测
- 保留原始错误
- 检测结果快照
- 同一目标前后两次结果对比

当前通用 `tool_execute` 是同步返回。规划必须给出能真正支持进度和取消的任务协议，不得只在前端隐藏 loading：

- 建议采用 `diagnosis_start` 返回 `runId`，后端任务通过 Tauri event 推送带单调 `sequence` 的步骤快照，`diagnosis_cancel` 触发 `CancellationToken`；必要时提供 `diagnosis_get` 用于事件丢失后的最终快照恢复。
- 说明运行任务注册表的生命周期、同一窗口并发策略、窗口关闭/应用退出清理、晚到事件隔离和重复取消的幂等性。
- 取消应传播到 DNS/TCP/TLS/HTTP 子任务；无法被底层 API 立即取消的阻塞调用必须放到受控线程并以结果丢弃/整体超时收口，不能无限占用 Tauri 命令线程。
- 每步执行生命周期至少区分 `pending`、`running`、`completed`、`blocked`、`skipped`、`cancelled`；结果判定另设 `success`、`warning`、`failed`、`unverified`。不要把生命周期和结论严重级别混进同一个字段。
- 所有结论必须引用产生它的 `evidenceId`；规则引擎只基于结构化证据生成结论，不解析展示文案。

避免用命令行文本解析作为唯一实现方式；优先评估稳定的 Windows API、Rust 标准能力或小型成熟依赖。

## 十一、UI/UX

规划一个清晰的诊断页面，至少包含：

1. 目标输入区。
2. 高级参数：
   - 协议
   - 端口
   - 连接 IP
   - SNI
   - HTTP Host
   - 指定 DNS
   - 代理策略
   - 超时
3. 分层诊断结果：
   - 代理
   - Hosts
   - DNS
   - TCP
   - TLS
   - HTTP
4. 每层状态：
   - 成功
   - 警告
   - 失败
   - 跳过
   - 无法验证
5. 原始证据展开区。
6. 结论摘要。
7. 复制和导出诊断报告。
8. 保留旧历史摘要；另行判断新诊断历史持久化和结果对比是否进入 MVP。

重点设计：

- 首次空态
- 正在检测
- 部分成功
- 用户取消
- 检测超时
- 无法访问代理或证书吊销端点
- DNS 多结果
- Hosts 与 DNS 冲突
- IPv4 成功但 IPv6 失败
- TLS 成功但主机名不匹配

交互还必须满足：

- 默认只展示目标输入、主动作和核心结论；连接 IP、SNI、Host、代理、DNS、超时等放在可发现的高级设置中，执行后仍能看到本次实际参数快照。
- 运行中逐步显示状态与已完成证据，主按钮切换为明确的“取消诊断”；取消后保留已完成步骤，不清空页面。
- 失败信息紧邻对应步骤，并给出可执行的恢复动作；颜色之外必须同时使用图标和文字表达状态。
- 原始证据默认折叠，支持单层复制；结论摘要与步骤证据双向定位，避免结论成为无法验证的黑盒。
- 完整键盘操作、可见焦点、合理 Tab 顺序；动态进度和错误使用适当的 `aria-live`，展开控件表达 `aria-expanded`。
- 不使用 Emoji 作为结构图标；复用项目现有图标与语义色、浅色主题和间距体系，不引入外部字体或 CDN。
- 小窗口下高级参数改为单列，结果区域避免嵌套横向滚动；大量 DNS 地址或证书链使用可折叠列表而不是无限增高卡片。

UI 保持 LazyCat 现有干净浅色风格。

## 十二、MVP 边界

首期建议包含：

1. URL、域名、IP 输入。
2. 系统代理、WinHTTP 和代理环境变量读取。
3. 对当前 URL 计算代理或直连决策。
4. Hosts 命中和冲突诊断。
5. A、AAAA、CNAME、PTR 查询。
6. 系统 DNS 与指定 DNS 对比。
7. PTR、系统 Hosts 和 LazyCat 本地历史候选域名；Windows DNS 缓存按 spike 结果决定是否在首期纳入。
8. TCP 连接测试。
9. TLS 握手、证书链、有效期、SAN 和信任状态。
10. HTTP 状态码、重定向和关键耗时。
11. IP 候选域名发现及正向验证。
12. 分层错误结论。
13. 复制或导出离线诊断报告。
14. 原位替换 `network` 入口并保留工具 ID。
15. 迁移旧收藏和历史摘要；保留 PING/TCP/UDP 单项探测的明确去留方案，默认不造成现有能力静默回退。
16. 后端任务进度、整体取消、晚到结果隔离和应用退出清理。

不要机械接受上述清单为一个大版本。规划前先给出 2 到 3 个短周期技术 spike，并用结果收敛 MVP：

1. Windows 代理画像与 PAC/WPAD 决策 API 可行性。
2. Windows 证书存储信任链、主机名和吊销检查的可控超时/离线语义。
3. Tauri 长任务事件、取消和最终快照恢复。

分阶段实施必须保证每阶段都能运行：

- Phase 1：原位入口、输入归一化、旧数据兼容、Hosts/有效解析/DNS/TCP、PING/UDP 单项探测、统一结果模型、取消与基础报告。
- Phase 2：TLS、HTTP、WinINET/WinHTTP 静态代理与环境变量代理决策、CONNECT、结论规则。
- Phase 3：PAC/WPAD、Windows DNS 缓存/NRPT/DoH、候选域名扩展、结果对比等增强能力。

如果 spike 证明某项能够低风险进入更早阶段，可以前移；如果不能，必须在 UI 中明确能力边界，不能用占位成功代替。

首期不做：

- 自动修改代理、Hosts、DNS 或证书
- 公网 IP 反查服务
- 声称查询 IP 对应的全部域名
- 全网端口扫描
- 网段扫描
- 远程机器配置修改
- 完整抓包工具
- 自研 DNS 服务器
- 完整证书管理器
- 强依赖本地大模型
- 自动携带浏览器 Cookie、系统凭据、Authorization 或客户端证书
- 静默执行任意脚本、任意自定义请求体或无限制下载响应体
