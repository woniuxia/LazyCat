# 上线包 Windows 归档替换重命名重试设计

## 问题与目标

本地归档执行完整替换时，旧归档目录已经成功重命名为本次运行的备份目录，但紧接着将 staging 目录重命名为原归档目录名时，Windows 10 可能返回 `ERROR_ACCESS_DENIED (os error 5)`。普通目录覆盖测试能够通过，说明基本权限和事务顺序有效；故障来自 Defender、索引器或其他文件系统过滤驱动造成的短暂路径占用窗口。

目标是在不改变完整替换事务、不吞掉持久权限错误的前提下，容忍 Windows 上短暂的错误 5，并保持失败后的旧归档回滚能力。

## 方案

在 `release_package_archive` 内增加一个小型目录重命名重试函数，统一供覆盖事务中的三类操作使用：

1. 将已有最终目录重命名为备份目录。
2. 将 staging 目录重命名为最终目录。
3. 提交失败时将备份目录重命名回最终目录。

仅在 Windows 且底层错误的 `raw_os_error()` 为 `5` 时重试。首次失败后依次等待 50、100、200、400、800 毫秒，最多执行六次重命名尝试。其他错误不重试，直接保留现有错误路径和上下文。

每次重试等待前检查取消状态；取消时停止重试并返回取消结果。重试耗尽后返回最后一次真实 I/O 错误，由现有提交或回滚逻辑生成包含源路径、目标路径和操作阶段的错误信息。

## 事务与错误处理

- staging 和备份仍位于最终目录的同一父目录，事务路径及 runId 隔离规则不变。
- 新目录提交成功后，继续按现有逻辑删除旧备份；本次修复不改变备份清理失败的处理语义。
- 新目录提交持续失败时，使用相同的有限重试策略恢复旧目录。
- 若恢复也失败，错误仍同时包含提交失败和回滚失败信息，不报告伪成功。
- 不改为目录内复制、文件合并或直接删除最终目录，避免旧文件残留和回滚能力退化。

## 测试与验证

通过可注入单次重命名操作的内部重试核心编写确定性单元测试，避免依赖特定 Windows 过滤驱动才能复现：

- 前几次返回错误 5、随后成功时，确认会重试并最终成功。
- 非错误 5 时，确认首次失败后立即返回。
- 错误 5 持续存在时，确认尝试次数有上限并返回最后一次错误。
- 覆盖事务现有的完整替换和失败回滚测试继续通过。

实现后运行上线包归档定向 Rust 测试、相关 `release_package` Rust 测试和 `git diff --check`。本次仅修改 Rust 归档模块及其内联测试，不涉及前端、bridge、配置或数据库。
