# 上线包按目标并行打包设计

## 背景与目标

现有上线包工具会串行执行前端构建、后端构建和统一归档。项目配置已经分别保存前后端工程、命令和产物路径，但每次运行必须同时处理两端；任一端失败后另一端不会继续，日志也以全局单列形式展示。

本次优化目标：

1. 前端产物路径既可手动输入，也可选择目录；后端产物路径既可手动输入，也可选择文件。
2. 每次运行可选择前端包、后端包或两者，确认弹窗默认全选，选择不写入项目配置。
3. 前后端分别在独立工作线程中完成构建和归档，一端失败不终止另一端。
4. 双端运行时允许部分成功，并保留成功端产物。
5. 日志归属于具体项目，在当前应用会话内按项目保留最近一次运行，并按前端、后端两列展示。

本设计替代 `2026-07-18-release-package-design.md` 中的串行执行、单一运行状态和全局日志部分；项目 CRUD、全局归档根目录、目录命名和 PowerShell 单段脚本语义保持不变。

## 范围与非目标

本次包含：运行目标选择、按目标校验、双工作线程、轻量协调器、部分成功状态、项目级会话日志、产物路径选择按钮和相关测试。

本次不包含：

- 多个项目同时打包；全局仍只允许一个活动 run。
- 数据库结构调整或日志持久化。
- 多次运行历史、日志搜索和日志导出。
- 修改已有工程配置字段、构建命令语义或前端 ZIP 模式。
- 用户主动取消后保留半成品。

## 页面与交互

### 产物路径

- 前端“产物路径”输入框保持可编辑，在尾部增加“选择目录”。选择结果以绝对路径写回，手动输入仍可使用相对工程目录路径或绝对路径。
- 后端“产物路径”输入框保持可编辑，在尾部增加“选择文件”。选择结果以绝对路径写回，手动输入仍遵循现有相对路径解析规则。
- 路径选择取消时不修改当前输入；选择错误使用现有显式错误提示。

### 确认弹窗

弹窗按以下顺序展示：

1. 归档目录名输入框。
2. 完整归档路径预览。
3. “本次打包内容”选择区，包含“前端包”和“后端包”，每次打开默认全选。

至少选择一项才能确认。选择只属于本次运行，不保存为项目偏好。

### 项目级运行日志

日志移入当前项目工作区，不再作为页面底部的全局卡片。每个项目在前端 module-level composable 中保留当前应用会话内最近一次运行态：整体状态、归档路径、整体错误、前端状态、后端状态和两列日志。

切换项目时只展示该项目的最近一次日志。开始新运行时只清空并替换当前项目的旧日志，不影响其他项目。日志列各自限长并独立自动滚动；宽屏并排，窄屏上下排列。未选择的目标显示“未选择”，不生成伪日志。

## 运行协议与状态

`start` 请求扩展为：

```ts
type ReleasePackageStartPayload = {
  projectId: number;
  folderName: string;
  targets: Array<"frontend" | "backend">;
};
```

后端拒绝空数组、未知值和重复值。前端正常只发送去重后的已选目标。

运行事件继续绑定唯一 `runId` 和 `projectId`。状态事件的 `phase` 扩展为 `frontend | backend | overall`：

- 工作线程向对应 phase 发送 `running`、`succeeded`、`failed` 或 `cancelled`。
- 协调器只向 `overall` 发送整体运行状态。
- 整体状态新增 `partially_succeeded`。
- 日志事件只使用 `frontend` 或 `backend`，每个线程的构建、产物校验和归档日志均留在本列。

整体终态规则：

- 所有已选目标成功：`succeeded`。
- 双端运行且恰有一端成功：`partially_succeeded`，返回最终归档路径。
- 所有已选目标失败：`failed`，不创建最终目录。
- 用户主动取消：`cancelled`，终止仍在运行的两个进程树并清理临时目录。
- 单端运行成功属于 `succeeded`，失败属于 `failed`。

## 并发与归档

沿用现有 `start` 创建的后台运行线程作为轻量协调器。协调器不执行前后端构建或复制，只负责：

1. 创建并持有本次 run 的共享临时目录和取消标记。
2. 为每个已选目标创建独立 PID 槽位并派生一个工作线程。
3. 等待工作线程结束并汇总结果。
4. 至少一个目标成功时执行一次最终目录原子重命名。
5. 发送唯一整体终态并清理活动 run。

每个工作线程独立执行：构建命令、产物类型校验、写入临时归档中的专属目标。线程失败只清理自己未完成的归档目标并返回错误，不设置全局取消标记，也不终止另一线程。

前端目标为所选目录本身或同名 ZIP；后端目标为所选文件。双端都选中时，协调器在启动工作线程前根据目标顶层名称检查冲突，冲突则显式拒绝启动。两个线程因此不会写同一个目标路径。

临时目录仍与最终目录同卷。运行期间不会暴露最终目录；协调器只在所有工作线程结束后提交成功产物。所有目标失败或用户取消时清理临时目录。最终目录在提交前被其他进程创建时显式失败，不覆盖已有内容。

## 取消与生命周期

活动 run 从单 PID 槽位改为前端、后端两个独立 PID 槽位。取消请求设置共享取消标记，并分别终止当前存在的 PowerShell 进程树。尚未启动命令或正在复制的线程通过取消标记退出。

用户取消是整体意图，不应用“部分成功保留”规则；即使一端此前完成，也清理本次临时目录且不提交最终目录。应用退出复用相同取消路径。

## 校验与错误处理

- 运行前始终校验归档根目录、目录名和最终目录不存在。
- 只校验被选目标的工程目录；未选目标的路径是否存在不影响本次运行。
- 产物可以在构建前不存在，构建成功后再校验：前端必须为目录，后端必须为文件。
- 保存项目配置仍要求前后端字段完整，不改变现有数据库约束与配置语义。
- 单端错误保存在对应目标状态中，并在对应日志列显示；另一端继续运行。
- 协调器错误、提交失败或所有目标失败必须显式形成整体失败，不伪造成功。
- `partially_succeeded` 必须同时携带最终归档路径和失败端错误，用户仍可打开成功归档。

## 前端状态模型

运行 composable 使用 `Map<projectId, ProjectRuntime>` 或等价响应式记录保存项目级会话状态。当前活动 run 仍由唯一 `activeRunId`、`activeProjectId` 和 pending start 绑定，迟到事件必须同时匹配 runId 与 projectId，不能覆盖其他项目或后续运行。

每个项目的前端、后端日志分别有界保留；现有总量 2,000 行可改为每列最多 1,000 行。组件分别持有两个日志容器 ref，并在对应列接近底部时自动滚动。

## 测试与验收

按测试先行实施：

1. Rust 输入测试：目标为空、未知、重复；按选择校验工程目录；单端运行不读取未选端。
2. Rust 归档测试：前端单端、后端单端、双端成功、前端失败后端成功、后端失败前端成功、双端失败、目标冲突和取消清理。
3. Rust 并发测试：两端命令可同时进入运行态；任一端失败不会阻止另一端完成；取消可终止两个 PID 槽位。
4. 前端纯函数与 composable 测试：默认全选、至少选择一项、整体状态标签、项目日志隔离、迟到事件过滤、单列日志限长。
5. 组件结构测试：前端目录选择、后端文件选择、确认弹窗字段顺序、项目内双列日志和窄屏布局。
6. 运行 `cargo test release_package --manifest-path apps/desktop/src-tauri/Cargo.toml -- --nocapture`。
7. 运行上线包相关前端测试、`pnpm typecheck` 和 `pnpm --filter @lazycat/desktop build:web`。

验收结果应满足：双端任务实际并发；一端失败不影响另一端；部分成功只提交成功产物；取消不留下最终目录；项目切换后日志不会串项目；路径既可输入也可按指定类型选择。
