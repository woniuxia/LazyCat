# 请求转发双 Tab 与日志自动刷新设计

## 概述

请求转发右侧工作台当前把规则表单、运行统计和转发日志串联在同一个 `workbench-scroll` 中。内容完整，但纵向层级过长，配置与观测两种任务互相挤占首屏空间；同时现有 2 秒轮询只更新规则状态和统计，没有重新查询日志，运行中的新日志只能通过切换规则、修改筛选或手动操作后看到。

本次将右侧工作台拆为“规则配置”和“运行观测”两个 Tab，分别承载编辑与观测任务，并在不新增定时器的前提下把日志刷新接入现有串行轮询。改动限于前端组件、样式、纯函数测试和现有源码结构守卫，不修改后端 IPC、数据库或日志模型，也不为本次局部改动引入新的 Vue DOM 测试框架。

## 目标

1. 把配置与观测拆成两个稳定入口，提升单个任务内的信息密度。
2. 保持工作台头部、左侧规则列表和已有业务操作语义不变。
3. 已有规则切换时记住本次会话最后使用的 Tab；新建规则始终进入配置。
4. 运行观测页中的日志随现有 2 秒轮询自动刷新。
5. 后台刷新不预先清空当前列表、不闪烁整块加载态，并维持从最新日志开始的连续分页窗口。
6. 延续既有请求令牌、选择意图和筛选快照保护，旧响应不能覆盖当前上下文。

## 非目标

1. 不增加用户可配置的刷新周期、暂停按钮或实时推送通道。
2. 不改变日志排序、筛选、分页、保留上限和后端查询参数。
3. 不修改规则 CRUD、启停、统计重置或日志清理的 IPC 合约。
4. 不引入新的全局状态、持久化设置或外部 UI 依赖。
5. 不重做左侧规则列表、工作台头部或应用整体视觉方向。

## 工作台结构

### Tab 模型

面板维护一个局部、非持久化状态：

```ts
type RequestForwardWorkbenchTab = "config" | "observability";
```

规则如下：

1. 默认值为 `config`。
2. 在已有规则之间切换时保持当前值，形成会话内记忆。
3. 创建草稿时强制切换为 `config`。
4. 草稿状态不展示“运行观测”入口，因为草稿尚无可查询的规则 ID。
5. 新规则保存成功后仍停留在 `config`，不因草稿转为持久化规则而自动跳转。
6. Tab 不写入 `user_settings`，离开工具后无需恢复。

### 页面分区

工作台头部继续显示规则名称、说明和运行状态。已有规则在头部下方显示 Tab 导航，Tab 内容各自使用独立滚动容器：

```text
rule-workbench
├── workbench-header
├── workbench-tabs（仅已有规则）
├── config-pane
│   ├── readonly-banner（仅配置页且规则只读）
│   └── config-scroll
│       └── RequestForwardRuleForm
├── observability-pane
│   └── observability-scroll
│       ├── 观测异常提示
│       ├── 转发统计
│       └── 日志筛选与列表
└── workbench-actions（仅配置页）
```

配置页显示只读提示、停止并编辑、删除、仅保存和保存并启动。运行观测页不显示配置只读提示和底部保存栏，避免与当前任务无关的操作占用空间；统计重置和日志清理仍留在对应区块内。

两个 Tab 使用独立滚动容器，使用户切换后能回到各自之前的滚动位置。切换 Tab 不销毁日志、统计或表单状态。

### Tab 交互与可访问性

复用项目在 `ApiMockPanel.vue` 等组件中使用的 Element Plus `el-tabs` / `el-tab-pane`，不自行实现另一套 Tab 键盘模型：

1. `v-model` 绑定局部 `activeWorkbenchTab`，由 Element Plus 提供 `tablist`、`tab`、`tabpanel`、唯一活动项 `tabindex="0"`、ARIA 关联和左右方向键行为。
2. 两个 `el-tab-pane` 均保持挂载，不使用 `lazy`，只隐藏非活动面板；各自内部的滚动容器和子组件 DOM 不销毁，因此滚动位置、日志展开状态和表单状态可以保留。
3. 配置页或观测页内的焦点不会在 Tab 切换后留在隐藏面板；切换由当前 Tab 按钮触发，焦点继续停留在活动 Tab 上。
4. 保持 Element Plus 的可见焦点样式，选中态同时使用文字强调和活动指示线，不能只依赖颜色。
5. Tab 切换不增加位移或缩放动画，并遵守 `prefers-reduced-motion`。

## 信息密度调整

密度优化保持“紧凑但可扫描”，不通过隐藏字段说明或缩小正文来换空间：

1. `workbench-scroll` 的外边距和区块间距适度收紧。
2. 规则表单卡片间距、内边距和标题下间距统一缩小，但保留现有四段结构。
3. 统计继续使用四列，降低卡片纵向内边距和标签/数字间距。
4. 日志列表缩小行间距与行内边距，保留摘要和五项事实信息。
5. 日志搜索与结果筛选保持同一工具行；窄宽度下仍按现有方式堆叠。
6. 使用现有系统字体和项目颜色变量，不引入 CDN 字体或新的单色视觉体系。
7. 主要正文不低于当前可读基线，状态、错误和焦点对比度保持清晰。

响应式行为保持现状：窄窗口下右侧工作台占满一列，统计变为两列，日志工具栏纵向排列，表单字段回落为单列。Tab 标签不得造成横向滚动。

## 日志自动刷新

### 根因

当前 `runPoll()` 每 2 秒调用 `refreshRules()`。`refreshRules()` 更新规则列表、运行状态，并在选择未变化时调用 `loadStats()`；它没有调用 `loadLogs()`，所以轮询期间日志不会变化。

### 刷新触发

复用现有串行 `setTimeout` 轮询，不新增第二个定时器：

1. `runPoll()` 完成规则和状态刷新后，如果当前为已有规则且“运行观测”Tab 可见，执行一次后台日志刷新。
2. 切换到“运行观测”Tab 时立即刷新统计和日志，不等待下一次定时轮询。
3. “运行观测”可见明确指 `activeWorkbenchTab === "observability"`，不与浏览器窗口可见性绑定。
4. 草稿、无选中规则、日志清理中、搜索防抖中、手动加载中或已有日志请求在途时不立即发起后台刷新，而是记录一次带规则 ID、选择意图和筛选快照的待执行刷新。
5. 当前冲突操作结束后尝试消费待执行刷新；上下文已经变化时丢弃，仍指向当前观测页时只执行一次，不重复排队。
6. 轮询仍保持串行调度，当前轮全部结束后才安排下一轮，不使用 `setInterval`。
7. 当最后一条运行规则在本轮变为停止时，本轮仍请求或排队一次终止刷新，再停止状态轮询；终止刷新不重新启动状态轮询。用户已经切换规则、离开观测页或改变筛选时，旧终止刷新按意图失效处理，由新上下文自己的即时刷新负责数据。

### 连续分页窗口

手动加载和后台刷新使用不同的呈现语义：

1. 首次加载、筛选变化和手动重试继续使用现有加载态，并以查询结果替换列表。
2. 后台刷新不预先清空 `logItems`、`logTotal`，也不打开整块 `logsLoading`。
3. 当前已加载数量记为 `loadedCount`，旧总数记为 `previousTotal`。第一次后台查询使用 `offset = 0`，`limit = min(1000, max(LOG_PAGE_SIZE, loadedCount + LOG_PAGE_SIZE))`，多取一页用于覆盖正常轮询间隔内的新增量。
4. 收到新的 `total` 后，目标连续窗口大小为 `targetCount = min(1000, total, max(LOG_PAGE_SIZE, loadedCount + max(0, total - previousTotal)))`。
5. 如果第一次结果少于 `targetCount`，说明两轮间新增量超过一页；再以 `offset = 0, limit = targetCount` 补一次查询。后端单规则最多保留 1000 条，补查不会越过现有 IPC 的 `limit <= 1000` 边界。
6. 最终直接用从 `offset = 0` 返回的连续结果替换列表并更新 `logTotal`，不与不连续的旧尾部拼接。这样 `logItems.length` 始终是数据库排序结果的连续前缀，后续“加载更多”仍可安全用它作为 offset。
7. 正常新增量不超过一页时，目标窗口会包含原已加载深度和全部新日志；极端情况下若日志总数因 1000 条保留上限保持不变，窗口仍优先保持连续，已经被后端淘汰的旧项必须从前端移除。

示意：

```ts
const probeLimit = Math.min(1000, Math.max(LOG_PAGE_SIZE, loadedCount + LOG_PAGE_SIZE));
const probe = await queryLogs({ offset: 0, limit: probeLimit });
const targetCount = Math.min(
  1000,
  probe.total,
  Math.max(LOG_PAGE_SIZE, loadedCount + Math.max(0, probe.total - previousTotal)),
);
const page =
  probe.items.length >= targetCount
    ? { ...probe, items: probe.items.slice(0, targetCount) }
    : await queryLogs({ offset: 0, limit: targetCount });
logItems.value = page.items;
logTotal.value = page.total;
```

目标窗口计算抽为 `requestForward.ts` 中的纯函数，实际实现仍需在每次查询写回前检查请求令牌、规则 ID、选择意图、关键词和结果模式快照。

### 并发与错误

1. 后台刷新不抢占搜索、防抖、加载更多、清理日志或规则切换产生的请求；冲突时只保留一个待执行意图，避免队列累积。
2. 任何筛选或选择变化都会使旧请求令牌和旧待执行意图失效，晚响应直接丢弃。
3. 首次或手动加载失败继续使用现有替换式 `logError`；已有日志上的后台刷新失败写入独立 `logRefreshError`，在列表上方显示非阻塞警告，不隐藏当前日志。
4. 下一次后台或手动刷新成功后清除 `logRefreshError`。后台刷新失败不得清空当前日志，也不改变规则运行状态或阻断转发。
5. Tab 切换只控制是否发起后台日志查询，不作为日志数据真值；切离观测页会使其待执行意图失效。

## 验证

### 自动化测试

至少覆盖：

1. 已有规则展示两个 Tab，草稿只进入配置。
2. 规则切换保持当前 Tab，创建草稿强制切回配置。
3. 配置页显示表单、只读提示和底部操作；观测页不显示这些配置操作。
4. 切入观测页会立即触发一次观测刷新。
5. 每轮运行态轮询在观测页可见时刷新日志，在配置页不刷新日志。
6. 后台刷新不会预先清空列表或打开整块首次加载态，失败时保留列表并显示非阻塞错误。
7. 无新增、少于一页新增、超过一页新增、总数缩小和达到 1000 条保留上限时，后台结果始终是连续前缀，`加载更多` 不跳过记录。
8. 后台刷新与筛选、加载更多、清理日志、规则切换竞态时旧响应不会写回，冲突结束后至多消费一次当前待执行刷新。
9. 最后一条规则停止的当前轮在无冲突时直接刷新，有冲突时排队一次终止刷新；完成后不再调度状态轮询。
10. 源码结构守卫确认使用两个非 `lazy` 的 `el-tab-pane`、独立滚动容器和配置页条件操作，不通过销毁面板切换 Tab。

### 最小视觉检查

当前仓库没有 Vue DOM 挂载测试基础设施；以下行为通过本地应用或仓库现有预览入口做手动冒烟，不用源码字符串断言伪装为运行时验证。检查配置、观测、草稿、运行只读、日志空态、日志错误态和窄窗口状态，确认：

1. Tab、头部、内容和底部操作没有重叠。
2. 配置与观测拥有独立滚动位置。
3. 统计和日志密度提升但文字未截断到不可辨认。
4. 375px、768px、1024px 和 1440px 宽度下无横向滚动。
5. 两个面板切换后 `scrollTop`、日志展开状态和表单状态不丢失。
6. Element Plus Tab 的活动项、ARIA 关联、Tab 键焦点和左右方向键行为可用。
7. 键盘焦点、选中态和浅色主题对比清晰。

## 风险与取舍

1. 双 Tab 会隐藏另一类信息，但配置与观测本就是不同任务；会话内记忆减少频繁切换成本。
2. 自动刷新只在观测页可见时请求日志，减少隐藏页面开销；切入时立即刷新保证数据及时。
3. 连续窗口查询在常规轮询中只发一次请求，只有两轮间新增超过一页时才补查；这比拼接旧尾部更可靠，并保证分页 offset 不产生缺口。
4. 不引入推送通道，日志最多延迟一个现有轮询周期，换取更小的实现和后端影响面。
