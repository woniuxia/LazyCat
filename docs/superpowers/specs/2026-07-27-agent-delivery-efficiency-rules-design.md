# Agent 交付效率规则设计

## 1. 背景

动作中心组合动作从专用开发环境入口演变为通用组合执行架构，最终形成跨前端、IPC、Rust、SQLite 和多个领域适配器的中大型功能。实现质量达到要求，但需求确认过细、范围升级后没有重新定界、并发与事务不变量审查偏晚，以及全量验证重复执行，显著拉长了交付时间。

现有 `AGENTS.md` 已规定最小闭环、定向验证、worktree 初始化和经验查阅，但尚未明确以下决策：

- 专用功能升级为通用架构时如何重新确认范围；
- 哪些设计细节需要用户确认，哪些应由 Agent 自主决策；
- MVP 与增强能力如何拆分；
- 状态型功能编码前必须明确哪些不变量；
- 结构性问题重复出现时何时停止叠加补丁；
- 定向、阶段和最终验证分别在何时执行。

## 2. 目标

1. 用少量高频规则减少碎片化确认、范围失控和后期结构性返工。
2. 保持当前质量标准，不以减少测试或隐藏失败换取速度。
3. 让简单任务继续直接执行，不为所有任务增加规格文档和检查清单。
4. 延续 `AGENTS.md` 作为规则单一事实源、`docs/experience/agent-workflow.md` 承载执行细节的现有结构。

## 3. 非目标

- 不增加脚本、Git Hook、CI 门禁或新的工程工具。
- 不修改 Superpowers 插件文件或其他外部 Agent 配置。
- 不改变默认在 `main` 工作、测试命令或提交规范。
- 不要求每个小任务编写设计文档或实施计划。
- 不降低并发、事务和跨模块功能的测试覆盖要求。

## 4. 方案

采用两层文档治理：根规则只保留会直接改变执行决策的条款，详细判断方法和模板写入 Agent 协作经验。

### 4.1 `AGENTS.md` 根规则

在“核心规则”或“开工闸门”中增加以下六项规则，具体措辞在实施时保持简短：

1. **范围升级重定界**：专用功能升级为通用架构，或任务新增持久化、后台任务、并发、恢复等复杂能力时，暂停实现，重新列出当前 MVP、后续阶段、非目标、影响范围和最低验证，并集中确认一次。
2. **批量确认**：架构方向明确后，低风险实现细节由 Agent 根据现有代码合理决策，不逐项请求确认；只有用户行为、数据模型、架构边界、破坏性操作或外部副作用发生变化时再次确认。
3. **MVP 分期**：通用能力先完成当前验收所需的最小闭环。历史、恢复、并行、自动触发等增强能力未进入本阶段验收标准时，不顺带实现。
4. **状态型功能闸门**：涉及并发、后台执行、事件、轮询或事务时，编码前明确唯一事实源、状态所有权、生命周期、事务边界、失败释放路径和恢复语义。
5. **结构性返工止损**：同一边界连续暴露两个并发、事务或状态一致性问题时，停止叠加局部修复，返回不变量和时序设计检查根因。
6. **分层验证**：局部修改执行定向验证，阶段完成执行相关测试和类型检查，最终交付或合并前执行完整验证；只有共享契约或构建配置变化时才提前补完整验证。

这些规则不使用文件数、代码行数或固定工时作为唯一触发条件。复杂度由行为和风险决定，避免小型跨文件修改被误判为大型任务，也避免少文件中的复杂状态机漏过闸门。

### 4.2 `docs/experience/agent-workflow.md` 执行细节

新增四个短节，供复杂任务按需查阅：

#### 范围升级重定界模板

重定界只输出一次集中摘要：

```text
当前目标：本阶段必须交付的用户结果
MVP：实现该结果所需的最小能力
后续阶段：有价值但不阻塞当前结果的能力
非目标：明确不做的行为
影响范围：涉及的领域、持久化、IPC 和 UI 边界
最低验证：本阶段完成的证据
```

如果用户已经明确选择，不重复询问；用户回复“继续”或“确定”后，按已确认摘要执行到下一个真正需要决策的边界。

#### 状态型功能设计检查表

编码前回答以下问题：

- 哪个存储或对象是唯一事实源，缓存和事件承担什么角色；
- 谁创建、持有和释放运行状态，所有成功、失败、panic 和启动失败路径是否释放；
- 哪些读取与写入必须处于同一事务，是否存在校验后状态变化的 TOCTOU；
- 并行 worker 是否共享了不可跨线程资源，失败是否相互隔离；
- 事件、轮询和请求晚响应如何避免旧状态覆盖新状态；
- 页面卸载、监听重建和应用重启后的状态如何收口。

#### 审查顺序

复杂状态功能按风险前置审查：

1. 数据模型、事务边界和状态机骨架完成后，先审查不变量及交错时序。
2. 领域执行与 UI 接通后，审查跨模块契约和用户反馈。
3. 合并前审查最终差异、遗漏测试和工作树边界。

修复审查问题后先验证受影响边界；除非修改触及共享契约或构建链，不重复执行未受影响的完整验证。

#### 三级验证矩阵

| 级别 | 触发时机 | 验证范围 |
|---|---|---|
| 定向验证 | 每个局部实现或修复后 | 对应单元测试、契约测试或最小检查 |
| 阶段验证 | 一个数据层、执行层或 UI 阶段完成后 | 相关测试集合，必要时增加类型检查 |
| 最终验证 | 功能验收完成、提交或合并前 | 任务要求的完整测试、类型检查、构建和 `git diff --check` |

失败必须显式报告。分层验证只减少无影响范围的重复执行，不允许把未运行的最终验证描述为通过。

## 5. 文档联动

- 修改 `AGENTS.md`，加入六项高频规则。
- 修改 `docs/experience/agent-workflow.md`，加入模板、检查表、审查顺序和验证矩阵。
- `CLAUDE.md` 已通过 `@AGENTS.md` 引用单一事实源，无需复制规则正文。
- `process.md` 已索引 Agent 协作经验，无需新增索引项。

## 6. 验证

1. 检查 `AGENTS.md` 六项规则完整且没有重复现有条款。
2. 检查根规则与 Agent 协作经验的措辞不冲突。
3. 检查 `CLAUDE.md` 仍只引用 `AGENTS.md`。
4. 检查 `process.md` 仍能路由到 `docs/experience/agent-workflow.md`。
5. 运行 `git diff --check`。

## 7. 验收标准

- Agent 能识别“专用功能升级为通用架构”并执行一次范围重定界。
- 已确认方向下不再对低风险细节逐项索要确认。
- 状态型功能在编码前有明确的不变量和事务边界。
- 同类结构性问题重复出现时优先回到设计，而不是继续叠补丁。
- 验证按定向、阶段、最终三级执行，最终质量门槛保持不变。
- 根规则保持简短，具体模板只存在于 Agent 协作经验中。
