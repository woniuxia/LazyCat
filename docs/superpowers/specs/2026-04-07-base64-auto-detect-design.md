# Base64 自动识别与类型同步设计

- 日期：2026-04-07
- 范围：`apps/desktop/src/components/EncodePanel.vue`、`apps/desktop/src/utils/base64.ts`、`apps/desktop/src/utils/base64.test.ts`
- 状态：已审校，待用户确认后实现

## 1. 背景

当前 LazyCat 的 Base64 面板位于 `apps/desktop/src/components/EncodePanel.vue`，交互方式是：

1. 用户先通过上方 `Standard / URL-safe` 单选按钮决定类型。
2. 点击“Base64 编码”时，前端按当前按钮状态调用标准或 URL-safe 编码通道。
3. 点击“Base64 解码”时，前端同样只按当前按钮状态调用对应解码通道。

现状问题不是编码能力缺失，而是“类型选择完全依赖手动切换”：

1. 用户粘贴一段已编码内容后，还要先判断它是 Standard 还是 URL-safe。
2. 如果按钮状态与实际输入类型不一致，点击解码就会直接失败。
3. UI 虽然保留了类型概念，但使用成本偏高，尤其是在频繁粘贴解码场景下。

用户已明确本次目标：

1. 自动识别输入内容的 Base64 类型。
2. 自动切换上方类型显示，减少手动切换。
3. 仍然保留 `Standard / URL-safe` 的类型概念与可见状态。
4. 编码场景下，当前显示类型仍然承担“目标编码类型”的语义。
5. 优先采用最小必要改动，不扩大到后端协议或额外设置项。

## 2. 改动目标

本次设计的明确目标如下：

1. 当用户在 Base64 输入框中输入或粘贴内容时，前端自动识别其类型，并同步更新类型显示。
2. 当用户点击“Base64 解码”时，若输入可被明确识别为 Standard 或 URL-safe，则按识别结果执行正确的解码通道。
3. 当输入不是 Base64 内容时，不自动重置类型，而是保留当前显示类型，继续作为编码目标类型。
4. 保留现有 `Standard / URL-safe` 切换控件，不移除手动切换能力。
5. 改动尽量限制在前端，不新增 Rust action，不新增 bridge channel，不引入新依赖。
6. 将识别逻辑抽成可测试的纯函数，避免全部堆在组件内。

## 3. 非目标

本次设计明确不包含以下内容：

1. 不新增后端“自动识别解码” action。
2. 不修改 `apps/desktop/src/bridge/tauri.ts` 的现有通道映射。
3. 不改变 Rust 侧标准 Base64 / URL-safe Base64 的实际编码与解码实现。
4. 不新增设置开关，例如“是否启用自动识别”“默认编码类型”等偏好项。
5. 不改造剪贴板建议系统；`clipboard-detect.ts` 仍保持现状。
6. 不额外扩展为“自动容忍空白、自动补 padding、自动修复非法输入”等更强容错功能；本次只优化类型识别与通道选择。
7. 不改变现有错误提示方式，解码失败仍沿用面板当前的 `ElMessage.error(...)` 反馈。

## 4. 已确认的产品决策

### 4.1 自动识别触发时机

用户已确认：

1. 输入框内容变化时就自动识别并更新类型显示。
2. 点击“Base64 解码”时再次按当前输入重新判定，并据此选择执行通道。
3. 即“输入时展示自动同步 + 解码时执行自动纠正”两者都要。

### 4.2 非 Base64 输入的处理

用户已确认：

1. 如果当前输入是普通文本或无法判定为 Base64，则不自动回退到某个固定类型。
2. 此时保留当前显示类型不变。
3. 当前显示类型继续承担“编码目标类型”的语义。

### 4.3 歧义输入的默认规则

用户已确认：

1. 如果输入只从当前工具实际支持的通道语义看，同时可被解释为 Standard 和 URL-safe，则视为“歧义输入”。
2. 歧义输入的默认显示类型为 `Standard`。
3. 这里的“歧义”定义进一步收紧为：仅使用 Standard / URL-safe 共享字符集、无 `=`、无 `+` `/` `-` `_`，且满足长度约束时，无法仅凭字符集判断用户意图。
4. 当前 LazyCat 的 URL-safe 通道对齐 Rust `base64::engine::general_purpose::URL_SAFE_NO_PAD`，即“URL-safe 字符集 + 无 padding”语义；因此带 `=` 的 URL-safe 变体不纳入本次自动识别成功范围。
5. 对仅使用共享字符集但带合法尾部 `=` 的输入，只要满足 Standard 当前 padding 规则，就直接视为明确 `Standard`，不再归入歧义分支。

### 4.4 手动切换与自动识别的优先级

用户已确认：

1. 若输入可以被明确识别为 Standard 或 URL-safe，则点击“解码”时以自动识别结果为准。
2. 若输入属于歧义输入，则点击“解码”时以当前手动选择的类型为准；若用户未手动切换，则按默认 `Standard` 处理。
3. 若输入不是 Base64，则自动识别不介入，继续以当前显示类型作为编码目标类型或解码尝试类型。
4. 这里的“手动优先”仅表示优先选择执行通道，不代表该通道一定解码成功；若用户手动切到当前工具并不支持的变体，仍按现有错误链路报错。

## 5. 方案对比

### 5.1 方案 A：前端 helper + 组件接入

做法：

1. 在前端新增一个轻量纯函数 helper，例如 `apps/desktop/src/utils/base64.ts`。
2. `EncodePanel.vue` 调用该 helper 完成输入识别、类型显示同步和解码通道选择。
3. 为 helper 补充 `base64.test.ts` 单测，覆盖明确类型、歧义输入和非 Base64 输入。

优点：

1. 改动仍然局限在前端，不触碰 bridge / Rust。
2. 识别逻辑是纯函数，可单测、可复用、可避免堆进组件。
3. 符合当前仓库“纯逻辑尽量抽出并测试”的协作约束。
4. 后续如果剪贴板识别或其他面板需要复用该规则，可以直接复用。

缺点：

1. 比“只改组件”多 1-2 个前端文件。
2. 需要补少量测试代码。

结论：**采用此方案**

### 5.2 方案 B：仅在组件内内联识别逻辑

做法：

1. 只改 `EncodePanel.vue`。
2. 在组件内直接写识别函数和解码路由选择逻辑。

不采用原因：

1. 虽然文件数更少，但纯逻辑会堆进组件，后续维护和测试都更弱。
2. 仓库已有“能抽成纯函数并做单测的逻辑，不要全部堆进组件”的明确约束。
3. 本次识别规则本身就是独立纯逻辑，抽 helper 的收益明确，成本也很低。

### 5.3 方案 C：后端新增自动识别解码通道

做法：

1. Rust 新增 `base64_auto_decode` 之类的 action。
2. bridge 增加新 channel。
3. 前端统一走自动解码通道，再回写显示类型。

不采用原因：

1. 改动链路更长，超出本次“最小必要改动”目标。
2. 即使后端承担了解码识别，输入时的类型显示同步依然需要前端参与。
3. 当前 Rust 侧标准 / URL-safe 能力已经足够，本次问题核心是前端交互，不是编码能力。

## 6. 设计方案

### 6.1 改动范围

本次最终改动范围控制为 3 个前端文件：

1. `apps/desktop/src/components/EncodePanel.vue`
   - 接入自动识别
   - 在输入变化时同步类型显示
   - 在解码时根据识别结果选择通道
   - 保留现有按钮与文案
2. `apps/desktop/src/utils/base64.ts`
   - 提供 Base64 类型识别纯函数
   - 提供解码场景下的类型决策纯函数
3. `apps/desktop/src/utils/base64.test.ts`
   - 为上述纯函数补单测

明确不改：

1. `apps/desktop/src/bridge/tauri.ts`
2. `apps/desktop/src-tauri/src/tools/encode.rs`
3. 其他面板与共享状态结构

`apps/desktop/src/utils/base64.ts` 的对外 API 本次也一并收口，至少包含：

1. `Base64DetectedKind = "standard" | "url-safe" | "ambiguous" | "none"`
2. `Base64ManualChoice = "standard" | "url-safe" | null`
3. `detectBase64Kind(input: string): Base64DetectedKind`
4. `resolveBase64DecodeKind(...)`：根据 `detectedKind`、`manualChoice` 和当前显示类型，返回最终解码通道类型

### 6.2 状态模型

保留当前已有的 `base64UrlSafe`，但补充两个轻量状态：

1. `detectedKind`
   - 枚举值：`standard`、`url-safe`、`ambiguous`、`none`
   - 语义：当前输入的自动识别结果
2. `manualChoice`
   - 枚举值：`standard`、`url-safe`、`null`
   - `null` 表示“当前输入上下文内尚无手动选择”
   - 只在歧义输入或非 Base64 输入场景下起兜底作用

状态语义如下：

1. `base64UrlSafe`：当前 UI 实际显示的类型，也是编码按钮的目标类型。
2. `detectedKind`：自动识别的结果，不直接取代 UI，但会影响自动同步和解码决策。
3. `manualChoice`：用户主动选择的类型偏好；在歧义场景下优先于默认值，在明确识别场景下不覆盖自动解码结果。

生命周期规则如下：

1. 组件初始化时，`manualChoice = null`。
2. 用户手动点击 `Standard / URL-safe` 时，写入对应 `manualChoice`。
3. 当输入被清空时，`manualChoice` 重置为 `null`。
4. 当输入从明确类型变回歧义类型时，若当前输入上下文中存在 `manualChoice`，则继续作为歧义场景兜底；否则按默认 `Standard`。
5. `manualChoice` 只影响歧义输入和 `none` 输入场景，不覆盖明确识别结果。
6. 需要与现有 `EncodePanel.vue` 的模块级 `encodeState` 持久化行为对齐：由于 `App.vue` 使用 `:key="activeTool"`，切换工具时 Base64 面板会被重建，但 `base64Input / base64Output / base64UrlSafe` 会从 `encodeState` 恢复。
7. 因此实现时 `manualChoice` 也必须与 Base64 输入状态一起持久化，并在组件重新挂载时直接从 `encodeState` 恢复；不能出现“显示仍是 URL-safe，但歧义解码决策已丢失”的偏差。
8. `detectedKind` 不要求跨切工具持久化，但组件重新挂载后若已恢复出非空 `base64Input`，应立即重新计算一次，使显示与解码决策状态重新对齐。

实现约束进一步明确如下：

1. `manualChoice` 本次明确落到 `EncodePanel.vue` 的模块级 `encodeState` 中，例如新增 `base64ManualChoice` 字段；不采用“依赖恢复后的输入内容和显示类型现场推断手动选择”的方案。
2. `detectedKind` 不进入 `encodeState`，只作为运行时派生状态存在；组件重新挂载后基于恢复出的 `base64Input` 立即重新计算。
3. `manualChoice` 只能在用户显式点击 `Standard / URL-safe` 时更新；自动识别导致的 `base64UrlSafe` 同步不得反写 `manualChoice`。
4. 实现上不要通过监听 `base64UrlSafe` 的通用 watcher 来推断“是否为手动切换”；应通过单独的用户交互入口记录 `manualChoice`，否则明确类型输入的自动同步会污染后续歧义输入的手动兜底结果。

### 6.3 识别规则

识别逻辑应保持保守，只在满足当前工具真实解码边界的前提下返回明确类型或歧义类型。

本次采用规则如下：

1. 先保留原始输入；`trim()` 只用于判断“是否全空白”，不作为后续识别和解码的预清洗结果。
2. 若 `trim()` 后为空，则返回 `none`。
3. 若原始输入包含空格、制表符或换行，则直接返回 `none`；包括首尾空白在内都不视为可自动识别输入。
4. 若输入包含 Base64 / Base64URL 统一字符集之外的字符，则返回 `none`。
5. 若同时混用了 `+/` 与 `-_` 两套专有字符，则返回 `none`。
6. 若包含 `-` 或 `_`，且不包含 `+` 或 `/`：
   - 若同时包含 `=`，则返回 `none`，因为当前工具的 URL-safe 通道对齐 `URL_SAFE_NO_PAD`
   - 若长度满足 `len % 4 == 1`，则返回 `none`，因为该形态按现有 Rust 解码器一定失败
   - 否则进入 URL-safe 候选校验
7. 若包含 `+` 或 `/`，则按 Standard 候选处理：
   - 若长度不是 4 的倍数，则返回 `none`
   - 若 `=` 只出现在末尾且数量为 0-2，则进入 Standard 候选校验
   - 否则返回 `none`
8. 若只包含字母数字和可选尾部 `=`，则按共享字符集候选处理：
   - 若包含尾部 `=`，长度必须是 4 的倍数，且 `=` 只能出现在末尾、数量为 1-2；满足后进入 Standard 可解码性校验
   - 若不包含 `=`：
     - `len % 4 == 0` 时进入 Standard / URL-safe 双侧可解码性校验
     - `len % 4 == 2` 或 `len % 4 == 3` 时进入 URL-safe 可解码性校验
     - `len % 4 == 1` 时返回 `none`
   - 其他情况返回 `none`
9. 上述分支只决定候选类型，不直接等于最终识别结果；最终返回 `standard`、`url-safe`、`ambiguous` 前，还必须通过与当前 Rust `STANDARD` / `URL_SAFE_NO_PAD` 语义一致的轻量可解码性校验。
10. 最终判定规则如下：
   - Standard 候选仅在 Standard 校验通过时返回 `standard`，否则返回 `none`
   - URL-safe 候选仅在 URL-safe 校验通过时返回 `url-safe`，否则返回 `none`
   - 共享字符集、无 `=`、且 `len % 4 == 0` 的候选：
      - 两侧校验都通过时返回 `ambiguous`
      - 仅 Standard 通过时返回 `standard`
      - 仅 URL-safe 通过时返回 `url-safe`
      - 两侧都失败时返回 `none`

轻量可解码性校验的实现约束如下：

1. 前端不要把浏览器 `atob`、Node `Buffer` 或其他运行时内置解码器当作事实来源，因为它们对 URL-safe、无 padding 和 trailing bits 的容忍度不一定与 Rust `base64` crate 完全一致。
2. 本次校验应由纯函数在前端自行完成，至少覆盖：
   - 字母表是否合法
   - 长度与 padding 规则是否合法
   - `=` 是否只出现在末尾且数量合法
   - 尾块未使用 bits 是否为 0，以对齐当前后端会拒绝的 trailing bits 非法输入
3. 实现方式可为“字符表索引 + 尾块 residue 校验”的轻量方案，不需要完整把输入解码成字节数组；重点是让识别结果与当前 Rust 解码边界保持一致。

说明：

1. 本次“自动识别”是交互优化，不试图从所有文本中完美推断用户意图。
2. 本次不对原始输入做预清洗后再提交解码，因此自动识别规则必须与当前后端可直接接收的原始文本保持一致。
3. 对仅由共享字符集组成的候选输入：
   - 无 `=` 且 `len % 4 == 0` 时，只有在两侧解码语义都成立时才返回 `ambiguous`
   - 无 `=` 且 `len % 4 == 2/3` 时，只有在 URL-safe 校验通过时才返回 `url-safe`
   - 带合法尾部 `=` 时，只有在 Standard 校验通过时才返回 `standard`
4. 这套规则优先对齐当前 `STANDARD + URL_SAFE_NO_PAD` 的真实解码边界，因此无法完全消除短纯文本与 Base64 候选之间的天然重叠。
5. 自动识别阶段不修改原始输入文本，也不提前替用户补 padding；真正提交解码时仍沿用当前输入原文与现有后端语义。

### 6.4 输入变化时的数据流

当 `base64Input` 变化时，执行以下流程：

1. 调用 helper 识别 `detectedKind`。
2. 若结果为 `standard`：
   - 自动将 `base64UrlSafe` 设为 `false`
   - 更新显示为 `Standard`
3. 若结果为 `url-safe`：
   - 自动将 `base64UrlSafe` 设为 `true`
   - 更新显示为 `URL-safe`
4. 若结果为 `ambiguous`：
   - 若 `manualChoice === null`，则默认显示 `Standard`
   - 若 `manualChoice` 有值，则保持手动选择
5. 若结果为 `none`：
   - 不自动更改当前显示类型
   - 继续保留当前类型作为编码目标类型

这保证：

1. 明确输入自动同步显示。
2. 歧义输入有默认值，但用户仍可接管。
3. 非 Base64 输入不会引发无意义的自动跳动。

### 6.5 手动切换的数据流

当用户点击 `Standard / URL-safe` 切换按钮时：

1. 立即更新 `base64UrlSafe`，让 UI 如实反映用户选择。
2. 记录 `manualChoice`。
3. 不直接清空 `detectedKind`，因为当前输入的识别结果仍然有参考价值。

优先级约束：

1. 对编码操作，始终以当前显示类型为准。
2. 对解码操作，若 `detectedKind` 为明确类型，则执行时以自动识别为准，并在执行前同步回对应显示类型。
3. 对歧义输入，解码时以当前手动选择为准；若 `manualChoice === null`，则使用默认 `Standard`。
4. 对 `none` 输入，自动识别不接管，沿用当前显示类型尝试执行。

### 6.6 编码、解码、互换、清空的数据流

#### 编码

点击“Base64 编码”时：

1. 不使用自动识别结果做强制覆盖。
2. 直接按当前 `base64UrlSafe` 选择标准编码或 URL-safe 编码通道。
3. 这样可保留“当前显示类型 = 目标编码类型”的产品语义。

#### 解码

点击“Base64 解码”时：

1. 先基于当前输入重新识别一次 `detectedKind`。
2. 若结果为 `standard`：
   - 强制使用标准解码通道
   - 同步显示为 `Standard`
3. 若结果为 `url-safe`：
   - 强制使用 URL-safe 解码通道
   - 同步显示为 `URL-safe`
4. 若结果为 `ambiguous`：
   - 以当前手动选择为准
   - 若无手动选择，则按 `Standard`
5. 若结果为 `none`：
   - 沿用当前显示类型尝试解码
   - 失败后保持现有报错行为

#### 互换

点击“互换”时：

1. 继续沿用当前实现，将输出写回输入，并清空输出。
2. 输入被替换后，新的输入内容再次触发自动识别。
3. 类型显示随新的输入内容重新同步。

#### 清空

点击“清空”时：

1. 清空输入与输出。
2. 将 `detectedKind` 重置为 `none`。
3. 清理仅在当前 Base64 输入上下文中有意义的手动兜底状态。
4. `base64UrlSafe` 保留当前 UI 值即可，不强制回退，符合“当前显示类型仍可作为后续编码目标类型”的语义。

### 6.7 UI 与错误处理

本次不改动 Base64 面板的整体 UI 结构：

1. 继续保留现有 `Standard / URL-safe` 单选按钮。
2. 不新增额外 badge、说明文字或提示条。
3. 不新增解码模式下的额外二次确认。

错误处理保持现状：

1. 仍由 `runBase64()` 捕获异常并通过 `ElMessage.error(...)` 提示。
2. 自动识别只负责更大概率选择正确通道，不对错误做吞并或重试。
3. 若输入本身非法，仍按现有错误链路反馈。

## 7. 验证方案

### 7.1 单测覆盖

新增 `apps/desktop/src/utils/base64.test.ts`，至少覆盖以下场景：

1. 明确 Standard 输入应识别为 `standard`，包括带合法尾部 `=` 的共享字符集输入。
2. 明确 URL-safe 无 padding 输入应识别为 `url-safe`，包括共享字符集且 `len % 4 == 2/3`、并通过 URL-safe 可解码性校验的无 `=` 输入。
3. 只包含共享字符集、无 `=`、`len % 4 == 0`、且同时通过 Standard 与 URL-safe 可解码性校验的候选输入应识别为 `ambiguous`。
4. 形态上看似合法、但因 trailing bits 非法而无法通过当前后端解码器校验的输入，应识别为 `none`；至少覆盖 1 个 Standard 示例和 1 个 URL-safe / 无 padding 示例，例如 `AB==`、`ABC=`、`AB`、`ABC` 中的代表样例。
5. 普通短文本的实际判型应由当前规则固定，并通过单测明确覆盖，避免后续回归漂移；至少固定 `hello -> none` 与 `test -> ambiguous` 这类代表性样例。
6. 带空格、换行或制表符的输入应识别为 `none`。
7. 同时混用 `+/` 与 `-_` 的输入应识别为 `none`。
8. 空字符串和全空白字符串应识别为 `none`。
9. 带 `=` 的 URL-safe 风格输入应识别为 `none`，与当前 `URL_SAFE_NO_PAD` 通道保持一致。
10. 含 `-_` 但长度满足 `len % 4 == 1` 的输入应识别为 `none`。
11. 解码决策函数在明确类型场景下应优先自动识别。
12. 解码决策函数在歧义场景下应优先 `manualChoice`，否则回退 `Standard`。
13. 解码决策函数在 `none` 场景下应沿用当前显示类型。

### 7.2 手工验证

至少验证以下交互：

1. 粘贴标准 Base64，类型自动切到 `Standard`，点击解码成功。
2. 粘贴 URL-safe 无 padding Base64，类型自动切到 `URL-safe`，点击解码成功。
3. 输入仅使用共享字符集、无 `=`、`len % 4 == 0`、且两侧校验都通过时，默认显示 `Standard`。
4. 输入仅使用共享字符集、无 `=`、`len % 4 == 2/3`、且通过 URL-safe 校验时，会被直接判为 `URL-safe`。
5. 输入仅使用共享字符集、但带合法尾部 `=` 且通过 Standard 校验时，会被直接判为 `Standard`，不再走歧义分支。
6. 形态看似合法、但 trailing bits 非法的输入不会被自动判为 `Standard`、`URL-safe` 或 `ambiguous`。
7. 歧义 Base64 下手动切到 `URL-safe` 后，点击解码按手动选择执行。
8. 输入普通文本时，类型不被自动重置，点击编码仍按当前显示类型输出。
9. 输入带空格或换行的 Base64 样式文本时，不自动切换类型；若直接解码，按现有后端行为报错。
10. 输入同时混用 `+/` 与 `-_` 的非法文本时，不自动切换到任一类型。
11. 带 `=` 的 URL-safe 风格输入不会被自动判为 `URL-safe`；若用户手动切到 `URL-safe` 并解码失败，仍按现有错误链路提示。
12. 含 `-_` 但长度满足 `len % 4 == 1` 的输入不会被自动判为 `URL-safe`。
13. 歧义输入下手动切到 `URL-safe`，切到别的工具再切回后，再次点击解码时仍按恢复后的手动选择执行。
14. 互换后，类型能根据新输入重新同步。
15. 清空后，旧输入相关的自动识别状态不会污染下一次输入。

## 8. 风险与回退

### 8.1 主要风险

1. Base64 与普通文本在字符集上存在天然重叠，自动识别不可能完美推断用户意图。
2. 为了对齐当前 `STANDARD + URL_SAFE_NO_PAD` 的真实解码边界，共享字符集、无 `=` 且 `len % 4 == 2/3` 的输入会被直接判为 `URL-safe`；这意味着少量短纯文本也可能被判成可解码候选，而像 `test` 这类 4 字符共享字符集文本也可能落入 `ambiguous`，这是当前最小改动方案下的可接受 trade-off。
3. 若候选条件继续收严，某些合法的短 Base64 输入又会失去自动识别能力。

### 8.2 控制策略

1. 将识别逻辑收口在纯函数里，先通过单测固定规则。
2. 识别逻辑保持保守，优先避免普通文本频繁误触发。
3. 保留手动切换按钮作为兜底，不把交互完全改成“只能自动识别”。
4. 解码失败时继续沿用现有报错，不引入隐式重试和额外分支。

### 8.3 回退方式

若后续验证发现自动识别体验不理想：

1. 仅需回退 `EncodePanel.vue` 对 helper 的接入。
2. Rust 与 bridge 无改动，无需跨层回退。
3. helper 和测试也可一并删除，回退成本较低。
