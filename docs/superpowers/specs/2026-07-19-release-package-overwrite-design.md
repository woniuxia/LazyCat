# 上线包目标归档覆盖设计

## 目标

当上线包目标归档目录已经存在时，在真正开始构建前提示用户，由用户选择取消或完整覆盖。未明确确认覆盖时，系统继续保持现有的拒绝写入行为。

## 交互流程

1. 用户在“确认打包”弹窗中编辑归档目录名、选择本次打包内容，然后点击“确认并开始”。
2. 前端调用后端检查当前项目归档根目录下的目标路径是否存在。
3. 目标不存在时，直接按现有流程启动打包，并传递 `overwriteExisting: false`。
4. 目标存在时，显示警告确认框：
   - 提示文案：`目标归档目录已存在。直接覆盖将完整替换其中的所有文件，此操作无法撤销。`
   - 取消按钮：`取消`
   - 确认按钮：`直接覆盖`
5. 用户取消时不启动任务；用户确认时以 `overwriteExisting: true` 启动任务。

确认框不增加第三种选择，也不在项目配置中持久化覆盖偏好。每次覆盖都必须由用户单独确认。

## 接口与数据流

- 上线包工具增加只读目标检查 action，输入 `projectId` 和 `folderName`，输出目标完整路径及 `exists`。
- `start` action 增加可选布尔参数 `overwriteExisting`；缺失时按 `false` 处理，保持旧调用方安全。
- 前端只依据目标检查结果决定是否显示确认框，后端归档提交仍独立校验实际文件系统状态，避免检查与启动之间的竞态绕过保护。
- 目录名继续复用现有 Windows 单级目录名校验；目标路径只能由已保存项目的归档根目录与目录名拼接，前端不能提交任意待删除路径。

## 覆盖提交策略

覆盖只发生在新产物已经完整写入 staging 后，构建或归档失败不得影响旧目录。

提交顺序：

1. 未允许覆盖且最终目录存在：返回“目标归档目录已存在”。
2. 允许覆盖且最终目录存在：将旧目录原子重命名到同一归档根目录下、本次 runId 专属的备份路径。
3. 将 staging 原子重命名为最终目录。
4. 新目录提交成功后删除备份目录。
5. staging 提交失败时，将备份目录重命名回最终目录；错误信息必须包含提交失败及回滚失败信息（如有），不能伪报成功。

备份路径和 staging 路径都必须绑定本次 runId；若任一路径预先存在则显式失败，不覆盖未知临时内容。取消只清理本次 staging，不删除已恢复或尚未替换的旧目录。

## 错误与竞态处理

- 目标检查后若目录才被创建：`overwriteExisting: false` 的任务在后端提交前失败，不静默覆盖。
- 用户确认覆盖后若目标目录消失：直接提交新目录，不视为错误。
- 用户确认覆盖后若目标路径是文件而不是目录：拒绝覆盖，避免把“归档目录覆盖”扩大为任意文件删除。
- 备份删除失败：新目录已经成功提交，但任务必须报告明确的清理失败，保留可识别的备份路径，避免静默遗留。
- 覆盖过程中的所有删除仅限经校验的 runId 备份路径；不直接递归删除用户给出的最终路径。

## 测试与验证

按测试驱动方式覆盖以下行为：

- 目标检查 action 对不存在目录、已存在目录及非法目录名返回正确结果。
- `overwriteExisting` 缺失或为 `false` 时继续拒绝已有目标。
- `overwriteExisting: true` 完整替换旧目录，旧文件不残留，新产物完整存在。
- staging 生成失败时旧目录保持不变。
- 最终提交失败时尽力恢复旧目录，并显式返回回滚结果。
- 目标为文件时拒绝覆盖。
- 前端仅在目标存在时显示二次确认，并传递正确的覆盖参数；取消时不调用 `start`。

完成后执行上线包 Rust 测试、前端上线包测试、`pnpm typecheck` 和桌面渲染层构建。

## 范围边界

- 不增加常驻复选框。
- 不支持合并目录或仅覆盖同名文件。
- 不持久化“默认允许覆盖”。
- 不改动项目配置模型和数据库结构。
- 不扩展为任意路径删除能力。
