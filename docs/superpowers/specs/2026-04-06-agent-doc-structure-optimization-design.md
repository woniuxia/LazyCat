# 代理规范文档结构优化设计

- 日期：2026-04-06
- 范围：`AGENTS.md`、`CLAUDE.md`
- 状态：评审通过，待用户复核

## 1. 背景

当前仓库中的 `AGENTS.md` 与 `CLAUDE.md` 已长期作为项目级代理协作规范使用，内容基本一致，也已经沉淀了较多稳定约束：

1. 项目背景、技术栈、目录结构与常用命令。
2. 前后端调用链路、工具接入方式与持久化说明。
3. Element Plus 样式覆盖、编码与中文规范、离线手册等高频注意事项。
4. Windows 构建、便携包、GitHub Release 与代理协作纪律。

现状问题不在于规则缺失，而在于文档越来越偏“连续说明文”，导致日常检索效率下降：

1. 多类信息并列堆积，遇到具体问题时需要从头扫读。
2. 高价值规则与背景信息混排，命中目标段落的成本偏高。
3. 同类约束分散在多个区域，维护时不容易判断应修改哪一节。
4. 终端阅读场景下，部分段落和表格不够利于快速定位。

用户已明确确认本次目标：

1. 以“日常检索更快”为优先目标。
2. 采用“中等重构”力度。
3. 允许重组章节、统一写法、压缩重复内容。
4. 不主动改变已有规则语义，不扩张规则边界。
5. 需要针对 agent 使用做专项优化，目标是同时提升：
   - 更快决策
   - 更少犯错
   - 更强执行力
   - 更利于工具使用
6. 上述 agent 专项优化中，优先级最高的是“更少犯错”。
7. 防错能力优先通过“场景化检查清单”体现，而不是只增加抽象原则。

## 2. 改动目标

本次设计的明确目标如下：

1. 将 `AGENTS.md` 与 `CLAUDE.md` 重组为更适合问题检索的结构。
2. 保留现有核心约束、命令、路径、流程和经验规则，不引入语义漂移。
3. 让代理在遇到具体问题时，可以先通过顶部导航快速定位，再下钻细节。
4. 让两份文档继续保持同构，后续维护时不出现“一个更新了、另一个没更新”的分叉。
5. 优化终端阅读体验，减少大段混排与低收益重复描述。
6. 在不改变既有规则语义的前提下，为 agent 增加一层显式的“决策闸门 + 场景化检查清单”。
7. 将最常见的执行漏项前置到固定检查区，减少遗漏同步、遗漏验证、遗漏高风险确认等错误。

## 3. 非目标

本次设计明确不包含以下内容：

1. 不新增一批新的开发规则、流程限制或审批要求。
2. 不改变现有硬约束的判断标准，例如 dev server、破坏性操作、可视化辅助等规则边界。
3. 不将两份文档分别定制成面向不同代理的两套内容。
4. 不将文档改造成复杂模板、超长表格或花哨排版。
5. 不扩展到 `process.md` 的结构重写；本次仅按既有规则引用它。
6. 不把整份文档改造成冗长 SOP；agent 优化仅覆盖高频易错场景。

## 4. 已确认的产品决策

### 4.1 优先目标

本次优化的首要目标不是“新代理快速上手”，而是“日常检索更快”。

因此文档组织方式应优先满足以下场景：

1. 代理遇到样式覆盖问题时，能快速定位到 Element Plus 相关说明。
2. 代理遇到编码、中文、路径、手册、构建、发布等问题时，能直接跳到目标章节。
3. 代理需要执行新增工具、构建打包、正式发版时，能快速找到操作入口和边界说明。
4. 代理在正式动手前，能快速判断当前任务属于哪个执行场景，并进入对应检查清单。

### 4.2 改动范围

本次允许的改动包括：

1. 重排一级、二级章节顺序。
2. 将同类内容合并到同一主题节下。
3. 将信息密度过大的段落拆成更稳定的小节编号。
4. 将部分终端下不利于检索的长表格改为列表。
5. 为文档增加导航型文本，例如“快速检索”“适用场景”“另见某节”。

本次不允许的改动包括：

1. 借重构之名引入新的规则语义。
2. 删除当前仍有效的关键约束。
3. 只改 `AGENTS.md` 或只改 `CLAUDE.md`。

### 4.3 Agent 专项优化范围

本次新增的 agent 专项优化，优先覆盖以下 4 类场景：

1. 文档规范改动
2. 普通功能开发
3. UI / 样式改动
4. 高风险改动

本次明确不单独新增“构建 / 打包 / 发布检查清单”；相关信息仍保留在原有构建发布章节中，但不作为本轮 agent 专项优化的一等公民场景。

## 5. 结构设计

### 5.1 目标章节结构

两份文档统一重组为以下一级章节：

1. `01. 文档定位`
2. `02. 快速检索`
3. `03. 项目速览`
4. `04. 开发与架构要点`
5. `05. 高频注意事项`
6. `06. 构建、打包与发布`
7. `07. 协作与变更纪律`
8. `08. 提交与验证`

该结构的核心意图如下：

1. `01-02` 负责快速判断文档用途与检索入口。
2. `03-06` 负责承载项目事实、开发要点和高频问题说明。
3. `07-08` 负责收口执行纪律与交付验证。

### 5.2 二级章节设计

为提升搜索命中率，以下大节应继续拆成稳定二级小节：

`02. 快速检索`

1. `02.1 问题导向索引`
2. `02.2 Agent 决策闸门`

`04. 开发与架构要点`

1. `04.1 常规工具调用链路`
2. `04.2 capture 特殊链路`
3. `04.3 前端组织`
4. `04.4 关键 composables`
5. `04.5 持久化与格式化`
6. `04.6 新增工具标准流程`

`05. 高频注意事项`

1. `05.1 Element Plus 样式覆盖`
2. `05.2 编码与中文规范`
3. `05.3 数据路径与目录策略`
4. `05.4 离线手册`

`06. 构建、打包与发布`

1. `06.1 构建与打包要点`
2. `06.2 产物类型`
3. `06.3 GitHub Release 正式流程`

`07. 协作与变更纪律`

1. `07.1 默认执行原则`
2. `07.2 可视化辅助`
3. `07.3 process.md 经验沉淀`
4. `07.4 文档规范改动检查清单`
5. `07.5 普通功能开发检查清单`
6. `07.6 UI / 样式改动检查清单`
7. `07.7 高风险改动检查清单`

### 5.3 顶部检索与决策层

`02.1 问题导向索引` 不重复完整规则，只提供问题导向入口。至少应覆盖：

1. 要新增工具，看 `04.6`
2. 改 Element Plus 样式，看 `05.1`
3. 遇到中文乱码或编码问题，看 `05.2`
4. 查数据目录、迁移与备份策略，看 `05.3`
5. 新增离线手册，看 `05.4`
6. 本地构建、便携包、WebView2，看 `06`
7. GitHub Release 正式发版，看 `06.3`
8. 代理协作、可视化辅助与 process 记录，看 `07`
9. 提交规范与推送前检查，看 `08`

`02.2 Agent 决策闸门` 负责让 agent 在正式动手前完成一次路径判断。至少应覆盖以下判断：

1. 当前任务属于哪个场景：
   - 文档规范改动
   - 普通功能开发
   - UI / 样式改动
   - 高风险改动
2. 当前任务是否存在同步约束：
   - 双文件同步
   - 多文件联动
   - 特殊样式覆盖联动
3. 当前任务是否有前置确认要求：
   - 危险操作
   - 大量文件改动
   - 数据结构或外部资源影响
4. 当前任务的最低验证要求是什么：
   - 结构一致性检查
   - 相关测试
   - `typecheck`
   - 必要时 `build:web`
5. 当前任务完成后是否需要经验沉淀：
   - 是否需要更新 `process.md`
   - 是否达到固化回规范文件的条件

为避免决策闸门变成孤立口号，应在该节中显式提示对应落点，例如：

1. 场景判断完成后，进入 `07.4-07.7` 中对应检查清单。
2. 同步约束判断可回看 `01. 文档定位` 中的双文件同步约束，以及 `05.1` 中的样式覆盖联动说明。
3. 验证要求判断可回看 `08. 提交与验证`，以及相关主题节中的最低验证提示。
4. 经验沉淀判断可回看 `07.3 process.md 经验沉淀`。

其中：

1. `02.1` 负责导航。
2. `02.2` 负责开工前的防错判断。
3. 二者都不替代正文，只负责让 agent 更快走对路径。

### 5.4 场景化检查清单设计

`07.4-07.7` 采用统一模板，降低 agent 执行时的切换成本。每组清单至少包含以下 4 段：

1. 开始前检查
2. 实施中检查
3. 完成前检查
4. 必须停下并确认用户的情况

4 组清单的职责边界如下：

1. `07.4 文档规范改动检查清单`
   - 关注双文件同步、语义漂移、规则遗漏、`process.md` 固化条件
2. `07.5 普通功能开发检查清单`
   - 关注调用链路、联动文件、类型与测试、dirty worktree、验证要求
3. `07.6 UI / 样式改动检查清单`
   - 关注视觉方向、Element Plus 覆盖、作用域、主题、弹窗、空态与边界态
4. `07.7 高风险改动检查清单`
   - 关注确认要求、影响范围、回退路径、数据与文件安全

该组清单的目标不是新增规则，而是把已有规则按执行场景前置成 checklist，减少 agent 漏项。

## 7. 写法设计

### 7.1 标题与编号

所有一级章节使用两位编号，二级章节按 `04.1 / 05.2` 形式编号。

设计原因：

1. 终端环境下便于搜索和引用。
2. 便于后续会话中直接用章节号沟通。
3. 能在继续扩充内容时保持稳定定位。

### 7.2 节开头的适用场景

每个一级大节开头增加 1-3 条“适用场景”提示，用于帮助代理快速判断是否应进入本节。

例如：

1. `05` 用于定位样式覆盖、编码、数据目录、离线手册问题。
2. `06` 用于本地构建、便携包、正式发版。
3. `07` 用于执行边界、可视化辅助和经验沉淀。
4. 检查清单节只服务于 agent 执行，不承担完整背景说明。

### 7.3 规则表达方式

规则类内容优先采用以下表达：

1. 先给结论性的规则。
2. 再给简短原因或后果。

目的不是增加解释，而是帮助代理判断“这条规则是否与当前问题有关”。

### 7.4 检查清单写法

新增的 4 组场景化检查清单，应遵循以下写法约束：

1. 每条检查项都应能被 agent 直接执行或对照。
2. 只写高频漏项，不写低收益背景描述。
3. 必须显式写出“何时必须停下确认用户”。
4. 清单是已有规则的执行映射，不单独发明新边界。

### 7.5 表格与列表的使用边界

仅保留真正适合对齐比较的表格：

1. 本地命令
2. Windows 产物类型

其余内容优先改为列表，尤其是：

1. 关键 composables
2. 新增工具流程
3. GitHub Release 正式流程

设计原因：

1. 终端中长表格扫描效率偏低。
2. 上述内容本质上是说明和步骤，不需要严格列对齐。

## 8. 实施步骤

实际改写 `AGENTS.md` 与 `CLAUDE.md` 时，应按以下顺序执行：

1. 先重建一级、二级章节骨架。
2. 再将原文内容按新结构迁移到对应章节。
3. 在迁移过程中去除明显重复表述，但不删除规则语义。
4. 补充“快速检索”“适用场景”“另见某节”等导航型文本。
5. 按 spec 补入 `02.2 Agent 决策闸门` 与 `07.4-07.7` 场景化检查清单。
6. 完成后对照两份文件，校验章节结构和关键规则是否一致。

## 9. 测试与验证要求

本次虽然是文档结构优化，仍需执行以下验证：

1. 检查 `AGENTS.md` 与 `CLAUDE.md` 的一级、二级章节结构是否一致。
2. 检查双文件同步约束是否仍保留。
3. 检查核心规则、构建发布、协作纪律、`process.md` 规则是否无遗漏。
4. 检查 `05`、`06`、`07` 等高频检索区块是否能覆盖主要问题场景。
5. 检查 `02.2 Agent 决策闸门` 是否能覆盖场景识别、同步约束、确认要求、验证要求、经验沉淀。
6. 检查 `07.4-07.7` 是否覆盖已确认的 4 类高频易错场景。
7. 检查是否引入新的规则语义或意外删除旧约束。

## 10. 验收标准

1. `AGENTS.md` 与 `CLAUDE.md` 已同步更新，且结构同构。
2. 文档顶部新增问题导向的“快速检索”入口。

6. 原有核心规则、命令、路径、流程和协作纪律均被保留。
7. 文档整体更适合终端下扫描和问题定位，也更利于 agent 执行时减少漏项。
8. 本次改动不引入新的规则语义，不改变现有约束边界。
