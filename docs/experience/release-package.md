## 2026-07-26：外部动作在线程启动前关联运行

**场景**：动作中心确认请求复用上线包现有确认链启动打包，并需要在打包结束后收口 dispatch 和上游 Todo。

**问题**：若 worker 启动后才关联 `dispatchId + runId`，快速失败可能先产生终态，留下永久 `running` 或待确认 dispatch；若在多个分支分别回写，部分成功、上传失败和取消容易映射不一致。

**解决**：后端 `start` 严格解析可选 `actionDispatchId`，占用运行槽后、`thread::spawn` 前校验动作、目标和状态并关联 run；关联失败释放运行槽且不启动命令。所有原始终态在统一 `emit_terminal_result` 中、状态事件和通知发出前回写动作中心。

**关键点**：只有 `succeeded` 映射成功并自动完成 Todo；`partially_succeeded`、`package_succeeded_upload_failed` 和 `failed` 都映射失败，`cancelled` 映射取消。普通手动打包没有 external run 关联，保持原通知和重试行为。动作中心只保存环境 ID，不接收 SSH 配置、密码或 Vault 秘密。

- `apps/desktop/src-tauri/src/tools/action_center/dispatches.rs`

## 固定环境使用稳定环境 ID

同一上线包项目只保存一份项目名和前后端工程目录，测试、生产环境分别保存构建与交付配置。环境表使用自增 ID 作为 IPC、运行、令牌和动作绑定的稳定引用，同时以 `(project_id, environment)` 唯一约束保留业务语义。

运行入口只接收环境 ID，后端加载环境及所属项目形成不可变快照。日志、状态、通知、上传预检和重试令牌都携带或绑定环境身份，不能依赖前端当前选择，也不能跨环境复用。测试环境默认且不得继承生产配置；生产启动必须经过显式确认。

## 生产构建分支由后端强制校验

前端、后端工程分别保存期望生产分支，默认均为 `master`。生产确认窗口可提前读取本次选中目标的当前 Git 分支并展示结果，但正式 `start` 必须使用数据库加载的环境快照再次校验，且校验发生在线程启动和上传预检令牌消费之前。分支不匹配、detached HEAD、非 Git 工作区或 Git 不可用都阻止生产构建，不提供忽略入口。

只检查本次选中的构建目标。测试环境不检查；上传失败重试和上传后命令重试复用既有构建产物，当前工作区分支不代表产物来源，因此不得重新检查或以分支变化阻断重试。

## 构建与归档是两阶段提交

构建成功不等于归档成功。先在临时 stage 生成并校验产物，再提交到最终归档目录；整体状态由各目标构建结果和归档提交共同决定。取消或失败不能留下看似可用的半成品。

## 多目标并行但状态独立

前端、后端等目标可并行执行，每个目标维护独立命令、日志 lane、结果与取消状态；overall 状态只聚合，不覆盖目标级错误。项目级日志和实时日志使用稳定运行 ID 关联。

## SSH 上传采用目标级有界并发

每个部署目标使用独立 SSH/SFTP 会话，双目标并发上限为 2；共享 `ssh2::Session` 本身没有吞吐收益。本地源清单校验、全部会话建立、远端冲突检查和目录预建必须在 worker 启动前完成；worker 只写入 temp 并校验。正式目标复核、backup、commit、rollback 和清理保持串行。所有 socket 集中注册，用户取消时关闭全部连接；内部目标失败使用独立 stop 信号，不能伪报为用户取消。进度按 100ms 节流，成功终态的上传总字节必须精确。首轮不做文件级并发、分块上传或可配置并发数，并发收益只通过受控 SSH fixture 评估。

## 归档目录是项目配置

归档根目录按项目持久化，最终路径以运行时返回为准。目录快捷入口只在存在成功 `archive_path` 时显示，不能用配置根目录冒充本次产物。

## 已有归档完整替换

检测到同名归档时先明确展示目标和影响，用户确认后执行完整替换。替换应在可恢复 stage 中完成，不能把新旧文件混合成不确定状态。

## 终态反馈在交付提交之后

`local_archive` 只有归档 commit 成功后才以 `succeeded/partially_succeeded` 表达可用本地产物并显示目录入口。`server_upload` 只有远端 commit 成功后才表达服务器上传完成；任一目标构建失败时不得开始上传，`partially_succeeded` 必须明确说明构建部分失败、未上传服务器。取消或完全失败不显示成功入口。长任务终态通过统一全局通知窗口呈现，通知内容与面板状态使用同一结果对象。

## 文件提交与后置命令是两个不可回滚阶段

服务器上传与上传后命令必须作为两个边界清晰的阶段处理：只有全部目标文件事务提交完成后，才按前端、后端顺序执行已配置命令。文件提交成功后已经产生不可回滚的线上事实；命令失败、取消或连接中断不能伪装成上传失败，也不能尝试回滚已提交文件或远端命令可能产生的副作用。

命令失败使用独立终态 `upload_succeeded_command_failed`，通知和日志必须明确“服务器文件已上传”。手动恢复只重试本次快照中明确失败的目标命令；已成功、已跳过和被用户取消的命令不进入重试。终态后的重试是新任务，必须重新完成主机信任与 SSH 认证，但不得重新构建、读取产物、写入 SFTP 或执行远端覆盖检查。

## 部署健康检查位于后置命令之后

服务器上传的执行顺序固定为远端文件提交、上传后命令、HTTP 健康检查。健康检查配置属于环境快照；启用时只有 HTTP 2xx 视为成功，首次失败后按固定 10 秒间隔重试，最大重试次数不包含首次请求。等待过程必须响应现有取消信号。

健康检查耗尽后使用独立终态 `deployed_health_check_failed`，提示“已部署但是验证失败”。该状态不得回滚已提交文件，不得创建上传或命令重试令牌；动作中心将其映射为失败且不自动完成 Todo。上传重试成功和上传后命令重试成功后也必须执行同一环境快照中的健康检查。

## 上传前必须完成真实预检

上传模式在构建前建立真实 SSH/SFTP 会话，校验认证、目标父目录、写入和重命名能力，并记录同名目标状态；正式上传前再次核对可信指纹和预检绑定。预检令牌必须与项目、目标和远程路径绑定、短期有效且只能消费一次，不能用端口连通性代替预检。

## 主机指纹先于认证

首次连接先展示 SSH 主机密钥类型和 SHA256 指纹，由用户明确确认后再发送密码或私钥认证。已信任指纹发生变化时必须阻止连接，同时展示旧、新指纹并要求显式更新信任，不能提供忽略或静默替换入口。

## 认证秘密只存在于一次性链路

私钥口令只从确认弹窗直接发送到后端预检；服务器密码只由 Rust 从已解锁的 Vault 读取。两类秘密都只保存在一次性、短期内存令牌中，不进入项目配置、数据库、日志、通知或重试描述。弹窗关闭、取消、启动成功和异常后都要清空私钥口令与预检状态。

## 密码库绑定只保存引用

账户密码认证的上线包项目只保存 Vault 服务器条目 ID。地址和账号在运行时从条目的非敏感元数据读取，密码仅在已解锁 Vault、主机指纹受信任后由 Rust 解密并交给一次性预检令牌。前端不得接收或提交服务器密码；Vault 锁定、条目缺失、类型变化或字段不完整必须显式阻止预检，不回退到手填密码。

## 远端目标使用完整替换事务

每个目标先上传到带运行 ID 的 temp 路径并校验完整性，再将正式目标切到 backup，最后提交 temp；失败或取消时按逆序恢复并清理。符号链接只删除链接本身，不跟随到目标。多个远端目标不具备跨路径原子事务，回滚只能尽力完成，失败时必须返回明确的恢复路径。

## 前端目录使用 tar.gz 单包传输

`server_upload` 的前端目录固定使用 `tar.gz` 单包传输，后端单文件仍直接通过 SFTP 上传。`ArtifactManifest` 继续作为构建产物和上传重试的唯一事实源：压缩前后都重新校验源清单，归档严格按 `entries` 顺序写入规范化相对路径，不重新遍历决定上传内容；拒绝绝对路径、路径穿越、符号链接和非普通文件，普通文件权限固定为 `0644`。本地压缩包由临时目录 RAII 持有，只存在于单次运行，不能写入数据库或重试描述。

前端部署事务顺序固定为：生成本地 tar.gz、上传到正式目标父目录下受 run ID 约束的唯一归档路径、校验远端归档大小、通过 SSH 解压到现有 `.__lazycat_tmp_<runId>` 目录、确认 temp 是目录、删除远端归档、复核正式目标，再进入既有 backup/commit/rollback。只有远端归档删除成功才允许 commit；大小不一致、解压失败、取消、连接中断或归档清理失败都必须清理归档和 temp，正式目录保持不变。解压命令由 `RemoteFs` 封装并对 POSIX shell 路径做单引号转义，gzip CRC 或 tar 退出码失败视为解压失败，不再递归 SFTP 校验前端文件。

真实预检选择前端目标时必须上传极小 tar.gz 探针并实际解压，通过 SFTP 校验探针文件内容后完整清理；服务器缺少 `tar + gzip`、解压异常或清理失败时不得签发预检令牌，也不降级为逐文件上传。用户取消压缩或解压使用各自阶段错误；取消关闭 SSH 后继续使用既有恢复连接清理机制。上传重试先执行 `manifest.verify_source()`，再生成新的临时压缩包；源清单变化继续明确拒绝。

上传进度只统计实际写入 SFTP 的网络字节：`totalBytes` 为前端压缩包大小加后端文件大小，`uploadedBytes` 为实际写入量，前端 `currentPath` 显示远端归档名。压缩和解压只写日志，不伪装成上传进度；日志记录前端文件数、原始/压缩大小、压缩率以及压缩、上传、解压耗时。

## 本地归档与服务器上传是互斥类型

项目以 `local_archive` 或 `server_upload` 作为唯一行为真值，不保留“先归档再上传”的组合模式。服务器上传不依赖归档目录，也不创建可交付的本地归档；前端只在单次运行内创建 RAII 管理的 tar.gz 传输包，归档内容是生成物目录内部文件，不把源目录本身套入远端目标目录。

上传失败使用 `package_succeeded_upload_failed` 并保留独立重试令牌。重试复用构建产物源清单，执行前必须校验源文件列表和大小没有变化，再结合新的 SSH 预检结果重建远端部署请求；源产物变化时明确拒绝重试。上传取消或失败不能破坏原线上版本，仍遵循远端完整替换事务。
